# 回折の設計

> 状態: **設計確定・実装前**（2026-08-03）。着手は メッシュ → プローブ場 → **ここ** の順。
> 旧 `DIFFRACTION_UTD.md` を置き換える。UTD を音声経路から外した経緯は `DEV_LOG.md` G章。

---

## 1. 目的

**回折の目的は「遮蔽感」と「開口部の方向」を伝えること。**
どのあたりから、どこから音が聞こえてきているか。

**回折そのものの物理的な精度は目的ではない。**

さらに、目的の中でも**優先順位がある**（2026-08-04 にユーザーが明示）:

> **位置による遮蔽量の具体性よりも、回折点への定位。**

つまり「どこから聞こえるか」＞「どれだけ遮られるか」。
この順位が、以下の設計判断すべての決め手になっている:

- 開口どうしの重みで **24dB 上限を外す**（上限があると遠い開口が同点になり定位がぼやける・§5-6）
- ゲインの合成をエネルギー加算から**最小 δ** へ戻す（連続でありさえすればよい・§5-6）
- 前川の式が**開口幅に反応しない**ことを既知の制約として受け入れる（ゲインの問題であって定位の問題ではない・§6-2）

この一文から以下すべてが導かれる。作品のコアが「周辺環境の変化を音で伝えること」であり、
個別現象の厳密性ではないため（`MEMORY.md` / portfolio-core-spatial-awareness）。

## 2. 出力

```cpp
struct DiffractionPath {
    Vec3  aperture;     // 鳴らす位置 = 音が抜けてくる開口。定位に使う
    float pathLength;   // listener → aperture → source の実長。遅延と距離減衰に使う
    float gain[6];      // 帯域別の減衰（前川の式・符号付き δ）
};

int findDiffractionPaths(const Vec3& listener, const Vec3& source,
                         DiffractionPath* out, int maxPaths) const;
```

**呼び出しは 1 回。音声タップも遮蔽感もこの結果だけを読む。**

現状は `diffractionContinuous`（ゲイン用）と `computeDiffractionSources`（方向用）が
別々に稜線を歩き、別々の重み・別々の上限を持っている。この重複が定数の食い違いと
挙動の不一致を生んでいるので、構造で消す。

持ち回る情報は上の 3 つだけ。UTD が必要としていたウェッジ幾何（入射角 φ'、回折角 φ、
ウェッジ角 n、Keller コーン角 β0）は**一切要らない**。非目標（§4）で精度を捨てたため。

## 3. 保証する性質

要件（§1）から直接出てくるものだけ。すべて回帰テストで固定する。

| # | 性質 | なぜ要るか |
|---|---|---|
| 1 | **連続性** — 何が動いても aperture も gain も飛ばない | 最優先。**不連続は「間違い」として聞こえる**が、数 dB のレベル誤差は気づかれない |
| 2 | **到達可能性** — aperture は実際に音が抜けてくる場所を指す | 壁を貫いて到達する稜線を開口と誤認していた（実機で観測） |
| 3 | **集中** — 開口が 1 つなら重みがそこに集まる | ぼやけると方向が伝わらない＝目的を満たさない |
| 4 | **周波数** — 低域ほど回り込む | **遮蔽感の正体はハイ落ち**。6 帯域ゲインがそのままローパスになる |
| 5 | **十分離れれば無効化される** — 縁から離れれば gain → 1.0 に戻る | 遮蔽していない場所で遮蔽感が残らない |

性質 1 は前川の式を使うことで**構造的に**保証される。δ は全候補の min を取っても連続で
（min は連続性を保つ。argmin が入れ替わっても値は飛ばない）、gain は δ のみの関数だから。
平滑化も重み付けも不要。

**性質 5 は「見通せたら 1.0」ではない。** 当初そう書いていたが誤り。
見通せていても、開口が波長に対して小さければ低域は減衰するのが正しい。

> 扉 90°（戸口 1m 幅・リスナー 3m 手前・音源 3m 奥）の第1フレネルゾーン半径は
> √(λ·d₁·d₂/(d₁+d₂)) = √(2.74×3×3/6) = **2.03m**。戸口の半幅 0.5m がこれをほぼ遮る。
> → **125Hz が −4.3dB 落ちるのは物理的に妥当**。実測 0.611 は誤りではない。
> 4kHz が 1.000（光線的に素通り）なのと合わせて、「戸口の向こうは高域そのまま・低域だけ落ちる」
> という知覚的にも正しい挙動になっている。

条件は「**縁から十分離れれば**」。開口の真ん中に立っているかどうかではない。

## 4. 非目標（明示的に捨てる）

- **回折レベルの物理的精度** — 数 dB のずれは問わない
- **3 次以上の回折**
- **別の部屋の音源を回折経路で追うこと** — 透過 ＋ 残響結合が担当する
- **すべての音源に回折を計算すること** — §5-9 の Full 段だけが対象

3 つ目は、屋内マルチルームを回折で解こうとすると大域構造（プローブ網・ポータルグラフ）が
必要になり、**「ベイクなし・完全動的」という作品の主張と衝突する**ため。
知覚的にも、3 部屋先の音が「どの角から回り込んでいるか」を人は聞き分けない。
「壁越しにこもって聞こえる」で足りる。

## 5. 決定事項

### 5-1. モデルは前川の式（`Core/maekawa.h`）

符号付き δ のみの関数。影で正・境界で 0・照射側で負。境界では両側 5dB に収束して連続。
N = 2δ/λ が波長で割るので高域ほど減衰が強く、性質 4 が自動的に満たされる。

UTD を採らない理由と実測値は `DEV_LOG.md` G-3〜G-5。要点だけ：
UTD は回折点の 3D 幾何に依存するので稜線が入れ替わると飛ぶ。重み付き平均・複素和・
エネルギー加算をすべて試して、最良 3.8dB / 最悪 17.6dB の段差が残った。前川は 0.35dB。

### 5-2. 次数は 2 次まで

**1 次で届かなかったときだけ、開口を新しい始点にして再帰する。**

```
findPaths(from, to, order):
    見通せる                  → 直接。終わり
    開口を求める（from から見た遮蔽物の稜線上）
    各開口 A について:
        A から to が見通せる    → from→A→to を 1 本として採用
        見通せない かつ order>1 → A を新しい始点にして再帰
```

- 開けた場所では 1 次で届くので **2 次のコストはゼロ**
- 上限（1 段あたり 4 本 × 2 段 = 最大 20 経路）でコストが確定する
- 鳴らす位置は **1 段目の開口**（人は「手前の角から聞こえる」と感じるため）

> **経緯（訂正）**: 一時ここを「1 次のみ」と書いていたが**誤りだった**。
> 根拠を「§4 で別の部屋は透過＋残響と決めたので 2 次の担当が残らない」としていたが、
> **L 字廊下の角は同じ空間内**であって「別の部屋」ではないので、§4 では消えない。
> ユーザーは当初から 2 次を要件として挙げており、こちらが独断でスコープを下げていた。
> 加えて「実行時に部屋の形状が変わる」を主張の中核に据えた以上、
> **手続き生成された曲がり角や、壁が消えてできた新しい通路**が普通に出てくる。
> そこで音が回り込まないと、主張と挙動が食い違う。

### 5-3. 開口の探索は稜線ベース。プローブは使わない

検討して却下した案：

| 案 | 却下理由 |
|---|---|
| **サンプリング**（扇状にレイを飛ばし、通った方向を開口とする） | **問題設定がずれている**。サンプリングは「直線が通る場所」を見つける手法だが、回折は「直線が通らないとき」の現象。屋内では 1 本も通らず、例外処理が本体になる。音源ごとに扇が要るのでスケールもしない |
| **ポータル**（空間に開口部を定義） | 事前オーサリングは動く形状と両立しない。実行時の自動抽出は重い前処理を要する難問 |
| **プローブ可視グラフ**（Steam Audio の pathing 相当） | 1 次回折には方向解像度が足りず（格子間隔で量子化される）、2 次以上は §4 で担当外にした。**担当範囲が残らない** |

SH プローブ場は**後期残響専用**として別途導入する。SH は方向分布を表せるが時間構造を
表せないので、正確な遅延が要る直接音・早期反射・回折には使えない。

### 5-4. 到達可能性は「貫通長」で判定する

回折点の可視判定で、その稜線を持つ箱を**丸ごと除外してはいけない**。
大きな壁で「壁を何メートルも突き抜けて遠い稜線に達する経路」が開口と誤認される。

一方、単純に「交差＝無効」にもできない。**厚みのある壁の稜線を回る経路は、幾何的に必ず
その厚みぶんを貫く**ため、正しい経路まで消える。

→ 分けるのは「通るか否か」ではなく **「どれだけ通るか」**。
箱のいちばん薄い方向を抜けるぶんまでは回り込みとして許し、それを超える貫通は棄却する。
`aabb.h` の `segmentObbPenetration()`。

### 5-5. 回折稜線はメッシュから抽出する（二面角でフィルタ）

当初「回折は簡略プロキシ（箱＝インスタンスの OBB）で扱う」としていたが、**これは破綻していた**。

> 壁と戸口が 1 つのメッシュだった場合、遮蔽判定（BVH）は「戸口を通る」と言い、
> 回折判定（OBB）は「中身が詰まっているので壁の外周を回れ」と言う。**同じシーンについて
> 2 つのサブシステムが矛盾した幾何を見る。** しかも戸口は本作でいちばん重要なケース。

バウンディングボックスは「どこに開口があるか」を定義上いちばん最初に捨てる。回折に使えない。

**正しくは、メッシュから回折稜線リストを抽出する。**
隣り合う 2 三角形が平面（二面角 ≈ 180°）なら、その稜線では回折が起きない。候補になるのは

- **二面角が有意に折れている稜線**（箱の角、壁の端、柱の稜）
- **境界稜線**（三角形が片側にしかない＝穴の縁、板の縁）

**候補数がテッセレーションに依存しない**のが要点。

| | 三角形 | 全稜線 | 回折稜線 |
|---|---|---|---|
| 箱 | 12 | 18 | **12** |
| 戸口つきの壁 | 24〜 | 40〜 | **16 程度**（外周＋戸口の枠） |
| 同じ壁を 10 倍細分 | 240 | 400 | **16 のまま** |

抽出はメッシュ登録時に 1 回（頂点ペアのハッシュで隣接を作り、二面角を測る。O(三角形数)）。
実行時は稜線リストを既存の候補探索にかけるだけで、`forEachDiffractionCandidate` の
「箱の 12 稜線を列挙する」部分がリストの読み出しに変わる。
**箱はこの一般形の特殊ケース**（二面角 90° が 12 本）なので、箱とメッシュが同じコードになる。

**帰結: 回折はメッシュの表現に依存する。** 当初「プロキシ箱なので回折はメッシュ対応の
影響を受けない」と書いたが誤り。回折はメッシュ対応の**後**に作らないと作り直しになる。

### 5-6. ゲインは最小 δ から。開口どうしの重みは上限なしの前川値

**当初「開口ごとにエネルギー加算」としていたが、実測して撤回した。**

```
実測（一本化してエネルギー加算にしたとき）
  影境界の隣接差   0.033 → 0.093
  ドアのゲイン連続 0.191 → 0.234
```

理由は、加算の前提である「**同じ物理経路を重複して数えない**」が、クラスタリングの離散性で
満たせないため。クラスタが分裂・統合する瞬間に和が飛ぶ。**min は連続なので飛ばない。**

§1 の優先順位（定位 ＞ 遮蔽量の精度）から見ても、**ゲインは連続でありさえすればよい**。
方向は開口ごとに別々に出るので、情報は失われない。

```
ゲイン       = maekawa(符号付き最小δ)          ← 連続
開口の重み   = maekawa(δ, 上限なし) の低域加重  ← 優劣をはっきり付ける
```

**重みで 24dB 上限を外す**のが定位に効く。上限をかけると遠い開口が全部 24dB で同点になり、
支配開口が薄まって方向がぼやける。実測でドアの集中度が 0.349 → 0.517 に改善した。

なお遮蔽感（残響ゲートなど）を透過と合成する場合は、上のゲインと透過の大きい方を採る。

現状は「透過 ⊕ 回折」を別々に出し、見通し状態を判定して max か diff かを切り替える分岐が
入っている（`AcousticFlowSceneDemo.cs` の `_directBands` 周辺）。
`findDiffractionPaths` の合計が「回り込んで届く総量」そのものなので、その分岐は消える。

**加算はエネルギー（二乗和の平方根）で、クランプを入れる。** 別経路は位相が無相関なので
エネルギー加算が妥当。ただし **`findDiffractionPaths` が同じ物理経路を重複して返さないことが
前提**である ── ここを守れないと過大計上で飽和する（2026-08-03 に稜線のエネルギー加算で
全域飽和させた。`DEV_LOG.md` G-3）。したがって §6-1 の「開口を同じものと見なす基準」は
この式の正しさに直結する。

### 5-8. 実行時の形状変化を第一級で扱う

**本システムの主張の中核。** 破壊はその一例にすぎず、本質は
「**レベルの形状が実行時に変わる前提で作られている**」こと。

形状（BLAS）と配置（インスタンス）を分けると、大半の変化が**配置の操作**になる。

| | 例 | 必要な処理 |
|---|---|---|
| 1. 移動・回転 | 扉の開閉、動く壁、エレベータ | `UpdateInstance` のみ。**再構築ゼロ** |
| 2. スケール変化 | **部屋の内寸を変える** | `UpdateInstance` のみ。**再構築ゼロ** |
| 3. 追加・削除 | 破壊、手続き生成、壁の出現 | インスタンスの増減。形状は事前登録済み |
| 4. 形状の生成 | ランタイム破砕、プロシージャルメッシュ | BLAS 構築（median-split、数百三角形で数十 μs） |

**1〜3 は形状の再構築が一切不要。** 4 だけが構築を伴い、それも 1 個ぶんで、
**レベル全体の再計算は決して発生しない。**
これが `Instance.geomId` のコメント「将来の **BLAS**(メッシュ)識別用」が意図していた構造。

既存の `ResizableRoom`（実行時に内寸を変える）と `SwingDoor` が、
レベル 1・2 の実証としてそのまま使える。

**対比（曖昧に「完全動的」と言うより具体的で反論されにくい）:**

| | 形状が変わったら |
|---|---|
| Project Acoustics | レベル全体の波動解を焼き直し（数時間） |
| Steam Audio | ベイクしたプローブ網が無効化 |
| Wwise Spatial Audio | Room / Portal を手で置き直し |
| **AcousticFlow** | **そのまま追従** |

**設計に課される要求:**

1. **メッシュインスタンスは非一様スケールを許す。**
   当初「一様スケール限定」としたが、レベル 2（部屋の内寸変更＝壁を伸ばす）と衝突するので撤回。
   コストの懸念も過大だった ── **ローカル空間のレイ方向を正規化しなければ `t` の意味が
   ワールドと一致する**ので距離比較は破綻せず、法線は逆転置（回転 R ＋対角スケール S なら
   **R·S⁻¹**）で済み、一般の逆行列は要らない。
2. `AF_SceneRemoveMesh` が他の geomId を無効化しないこと（vector の詰め直しではなくフリーリスト）
3. 稜線抽出が実行時に走れること（O(三角形数)・ハッシュ）
4. **SH プローブ場を、形状が変化した近傍で優先的に無効化・再収束させる**
   （壁が消えたのに響きが変わらなければデモとして無意味）
5. **インスタンス数の急増**（壁 1 枚 → 破片 50 個）。現在 `scene` はインスタンスを線形走査
   しているので、TLAS（インスタンスの BVH）が要るかは実測してから決める

**デモは連続変化と離散変化の両方を持つ。**
スイングドアと部屋のリサイズは*連続*変化（滑らかさの証明）、壁の増減は*離散*変化
（動的性の証明）。前者は本システムが最も苦労して作った性質、後者はベイク不可能さが一目で伝わる。

> ※システム全体としての主張の書き方はポートフォリオ文書（未作成）に属する。
>   ここに書いてあるのは、回折の設計がそれをどう支えるかの部分。

### 5-7. 開口 0 本のときは透過のみ（要レビュー）

完全に囲まれていて回り込みも無い場合、透過だけが届く。
④キーで封鎖した部屋の外の音がこれにあたる。**透過だけで正しい。**

### 5-9. 回折を計算する音源は「Full 段」だけ（同時音源数の扱い）

`findDiffractionPaths` は音源ごとなので、音源数がそのまま倍率になる。
**固定の想定音源数は決めない。** 代わりに詳細度の段を設け、上限を設定値で持つ。

| 段 | 計算 | 目安 |
|---|---|---|
| **Full** | 直接 ＋ 早期反射 ＋ **回折経路** ＋ 残響送出 | 既定 8 |
| **Reduced** | 直接（透過のみ）＋ 残響送出。**回折探索と早期反射を省く** | 〜16 |
| **Virtual** | 音を出さない。位置だけ追う | 上限なし |

選別は**可聴性の見積もり（透過 × 距離）**で行う。エンジンが毎フレーム出している値なので追加コストは無い。

これは既存システムの**バーチャルボイス**と同じ構造だが、落とす対象が違う。
Wwise / FMOD / Unreal / Unity が落とすのは **DSP のコスト**（音量しきい値を下回った音を
バーチャル化し、再生位置だけ進める）。本システムで高いのは **音源ごとの音響計算**なので、
落とすのは**音響の詳細度**になる。

→ **回折のコストは音源数ではなく Full 段の上限で決まる。**
   ホラーで環境音・足音・物音・敵が同時に鳴っても、遮蔽の変化が意味を持つ音は数個なので 8 で足りるはず。

段組みそのものの実装は本章の範囲外（別途）。ここでは
**`findDiffractionPaths` が「Full 段の音源にだけ呼ばれる」前提で設計されていること**を固定する。

### 5-10. フレネル・キルヒホッフ積分は試して保留にした

**元の法則に戻る**試みをした。前川も UTD も、この積分の近似（実験式／漸近展開）にすぎない。

> 音源と受音点の間に面を置く。受音点の音場は、その面のうち**塞がれていない部分**にわたる
> 積分で決まる。各点の寄与は経路長に応じた位相 e^{-jk(r1+r2)} を持つ。

動機は §6-2（前川は開口幅に反応しない）で、扉の開き具合が piecewise constant になっていたこと。
実装は `Core/kirchhoff.h`（矩形開口の解析解）＋ `Scene::diffractionKirchhoff`。
素朴なサンプリングは高域で破綻するので（4kHz で 6mm の隙間を解像するには 1万点規模）、
**開口を矩形で近似して解析的に解く**形にした。

**解析解そのものは正しい。** ナイフエッジで 0.5（−6dB）を再現し、古典解と一致する。

**破綻したのは幾何のフィッティング**。開いた領域は矩形ではない（扉が開くと板が室内に振れて
開口の一部を塞ぐので、L 字や複数の島になる）。矩形1つで当てると角度によって当て方が飛ぶ。

```
実測（0°→90°、キルヒホッフ 125Hz）
  0.183 → 0.104 → 0.481 → 0.172 → 0.421 → 1.000 → 0.517
                          ↑跳ぶ    ↑落ちる           ↑全開なのに 0.517（誤り）
```

途中「0〜10° で隣接差 0.000」という良い数字が出たが、**連続だったのではなく
ひとつの開口に張り付いて動いていなかっただけ**だった。

**保留の判断**: 方向性は正しいが幾何の分解に腰を据えた実装が要る。§1 の優先順位では
定位が先で、開口幅への追従はゲインの精度なので後回しにできる。
コードは比較用に残す（`AF_SceneComputeDiffractionKirchhoff`。UTD と同じ扱い）。

再挑戦するなら、開いた領域を**複数の矩形に分解**して複素和を取る方向（矩形なら加算できる）。

## 6. 未決事項

### 6-1. 開口を「同じもの」と見なす基準

現状はリスナーから見た方向 25° 以内で融合している。
ドアと窓が近いと 1 つに融合してしまう。複数開口を出したい（要件）ので、この基準は効く。
**実験しながら調整する**方針（数値を先に決めない）。

### 6-2. 前川の式は「衝立」のモデルであって「開口」のモデルではない

**注意: 当初ここを「見通せているのにこもるのはバグ」と書いていたが、その断定は誤りだった。**
実測値 0.611（125Hz）はフレネルゾーンで検算すると**物理的に妥当**（§3 性質 5 参照）。

残る問題は値そのものではなく、**モデルの適用域**である。

前川の式は半無限スクリーンの挿入損失の実験式で、受音点が照射側にあるとき
（N が負、−0.2 < N < 0）も 0〜5dB の減衰を与える。単独の衝立ならこれは妥当。
一方**戸口のように両側に縁がある「開口」は、本来 Babinet の相補問題**であり、
減衰は**開口の幅**に依存する。ところが**前川の式は開口幅を入力に持たない**（δ だけ）。

→ 今回たまたま妥当な値になったが、**開口幅を変えたときに正しく追従する保証がない**。
戸口を 2m に広げても 0.5m に狭めても、最小 δ が同じなら同じ減衰を返してしまう。

**判断: 既知の制約として受け入れる。** §1 の優先順位（**定位 ＞ 遮蔽量の精度**）から、
これは**ゲインの問題であって定位の問題ではない**。開口の位置と方向は正しく出ている。

実際に現れる症状（記録しておく）:

- 扉を 0°→10° 開いても 125Hz のゲインが変わらない（0.415 のまま）
- 戸口の幅を 0.5m と 2m に変えても同じ値を返す

対処を試みた記録は §5-10（フレネル・キルヒホッフ積分。方向性は正しかったが幾何の分解で保留）。

## 7. 検証：スイングドア

要件の 5 性質を**一度に**検証できる唯一のシーン。回帰テストとデモ動画を兼ねる。

押して開くドア。蝶番で回転し、開くにつれて直接聞こえる角度範囲が広がる。

- 隙間が開き始めた方向の音源 → 早い段階からダイレクト
- 振れた扉の板が覆う側の音源 → 扉が振り切るまで透過のまま

扉の角度を 0°→90° に連続に振り、各角度で測る。

| 測るもの | 対応する性質 |
|---|---|
| aperture が隣接角度で飛ばないか | 1 連続性 |
| aperture が扉の板の裏を指さないか | 2 到達可能性 |
| 支配クラスタの重み | 3 集中 |
| 低域 > 高域 | 4 周波数 |
| 直接見通せる角度で gain → 1.0 に繋がるか | 5 境界の一致 |

**このシーンは作品の主張そのものでもある。**
扉の角度ごとに音場が変わるのは、Project Acoustics が原理的にできず（角度ごとに焼き直せない）、
Wwise なら手動オーサリングを要求する領域。ベイクなしの価値を 1 シーンで示せる。

読み取れること：

- **開口位置が 7.5° 刻みで階段状**（同じ値が2回続いて跳ぶ）。扉に追従していない。
  0°→15° では y が 4.53 → 1.60 と **3m 飛ぶ**。扉の上を越える経路から横を回る経路への乗り換え。
- **75° 以降、減衰が残っているのに開口が 0 本**になる。
  **見通しが開通した瞬間に定位が消える** ── 最も定位が効いてほしい場面で情報が無くなる。
  原因は §2 の重複：ゲイン側は `blockerMargin` を広げて候補を探すが、方向側は既定の 0 のまま。
  **これは疑いの余地なく不具合。**
- **開き切りの 125Hz 0.611 は不具合ではない。**
  当初「見通せているのにこもる＝バグ」と判定して合格基準を「> 0.9」と置いたが、**誤りだった**。
  フレネルゾーン（半径 2.03m）を戸口の半幅 0.5m がほぼ遮るので、低域が −4.3dB 落ちるのが正しい。
  4kHz が 1.000 なのと合わせて、知覚的にも妥当な挙動。
  **間違った合格基準のまま作り直すと、正しい挙動をバグとして潰していた。**

**未達は `check()` にしていない。** 「壊れた」ではなく「まだ作っていない」なので、
赤いままのスイートは信用されなくなるため。作り直しのときに目標値をそのまま `check()` へ格上げする。
