# 開発システム ── 資料用の詳細

2026-08-24。`portfolio/acousticflow_portfolio.html` に載せるための原稿。
数字はすべて実測。推定値は「推定」と書く。

---

## 0. 全体像 ──「いつの音を見るか」で分かれている

| | 見る時間 | 道具 | 出口 |
|---|---|---|---|
| **これから** | まだ鳴っていない音を決める | 調整卓 | 材質が変わる |
| **いま** | 鳴っている最中 | AF ツール | 目と耳で切り分ける |
| **さっき** | 直前の 26 秒 | キャプチャ | 回帰テストを吐く |
| **ずっと** | 二度と壊れないように | 回帰テスト | 442 件の検査 |

★**一周する**のが設計の狙い:

```
調整卓で狙いを決める →（鳴らす）→ AF ツールで切り分ける
   →（変だ）→ キャプチャで録る →（走査）→ 回帰テストを吐く → 以後ずっと守られる
```

この一周が閉じていることが、道具を「作った」ではなく「効いている」にしている。

## 1. キャプチャ（サウンドデバッグツール）

### 一行

**常時録音した「入力」と「音響の出力」を、あとから走査して破れを見つけ、
そこから回帰テストを生やす道具。**

### なぜ「録画開始」を押させないのか

変な音は**気づいたときには終わっている**。押してから録るのでは間に合わない。
→ 常に溜めておいて、押したら**さかのぼって**切り出す（前 21 秒＋後 5 秒）。

⚠ 21 秒なのは、**畳み込み器の遅延線が冷えている**ぶんを捨てるため。
T-21s から流して T-20s から見せる。器の内部状態を保存する代わりに 1 秒余分に録って暖める。

### 設計判断①: 録るのは「結果」ではなく **「入力」**

エンジンは毎フレーム、ホストから
`動いた実体 → リスナー位置 → 音源位置 → Update` を押されて動く。
**その押している値を録って押し直せば、それが再現になる。**

- イベントログからの再合成が要らない
- RNG もボイススティールも記録しなくてよい（そもそも無い）
- 容量は 26 秒で **6〜7 MB**（うち 5 MB はマスター PCM）

### 設計判断②: 判定は**録音後**にする（実時間の警告にしない）

- オーディオスレッドで判定しない ＝ 確保もロックも要らない
- ★**検出器を後で良くしたら、昔のキャプチャに付け直せる**

★この判断が実際に効いた瞬間がある。実機のキャプチャに初めて当てたとき
**816 件**が光って使い物にならなかった。検出器を直して**同じファイルに当て直し**、
816 → 381 → まとめて **5 か所**まで絞れた。
実時間で判定していたら、録った瞬間の 816 件で固定されていた。

### 設計判断③: 検出器は**この作品で実際に出たバグ**から作る

汎用のプロファイラが持つ項目（クリッピング・LUFS）ではなく、
自分の模型の破れ方から逆算する。**思いついた検出器は入れない。**

### 破れの型紙 ── 9 つ

| # | 型紙 | 縛るもの | 元になった実際のバグ |
|---|---|---|---|
| 1 | 跳ばない | 隣接差が閾値以内 | 閉扉で 23.0 / 19.7 dB |
| 2 | 向きが正しい | 掃くと単調に動く | 開口へ近づくのに小さくなる |
| 3 | 経路が消えない | どこでも見つかる | 2 次回折 0.486 → 0.000 |
| 4 | 幻が出ない | 遮蔽されているのに帯域がまっすぐ、が無い | 閉扉の幻（低−高 ≈ 0） |
| 5 | 決定的 | 同じ入力で 2 回走らせて一致 | 並列化で BVH が競合 |
| A | 比が保たれる | 2 つの量の比が範囲内 | 尾だけ **8.3 倍**（掛け忘れ） |
| B | 設定不変 | 速くするだけの設定で音が変わらない | 並列／共有バス／分割 |
| C | 効いている | 掃引の振れ幅がある | 隙間幅が効かない |
| D | 上限を超えない | 振幅比が 1.0 以下 | タップ 0.88 → **1.76** |

★**2 と C は対で使う。** 単調性だけでは**定数が合格する**
── それが「隙間幅が全く効かなかった」当時のコードが通っていた形。

★**A と B と 5 は別物。** A は「一定して間違っている」（跳びでも幻でもない）、
5 は「同じ設定で 2 回」、B は「**設定を変えて**」。

### ★検出器そのものを検査している

**「破れなし」は、その型紙が効いている証明にならない。**
黙っているのが「健全だから」か「壊れていて何も見ていないから」か区別できない。
── これは型紙 C（効いている）の、**検出器自身への適用**。

→ 9 つ全部に**当時の実数**（19.7dB / 8.3 倍 / 1.76 / 0.486→0.000 …）を食わせ、
**発火すること**と、健全なデータで**黙ること**の両方を検査している（16 件）。

その中に、こういう検査が入っている:

```
[OK] ★型紙2 は定数を通してしまう（だから C と対で使う）
```

**バグを見逃した形そのものが、検査として残っている。**

### 走査と回帰テストが**同じ関数**を呼ぶ

別々の式にすると「道具は見つけたのに検査は通る」「検査は落ちるのに道具は黙る」が起きる。
→ 型紙を 1 箇所（`AcousticEngine/src/Debug/detectors.h`）に置き、
Unity のパネルも `AfCapScan` も回帰テストも**同じ関数**を呼ぶ。
一致することを検査で毎回縛っている:

```
[OK] [ABI] 走査の結果が検査の経路と一致する (ABI 18 件 / 直 18 件 / 食い違い 0)
```

### 見つけた破れ → 回帰テストの生成

★**絶対値を焼いてはいけない。**
フレーム 412 の 0.0837 を焼くと、**正当なチューニングのたびに落ちて、すぐ信用されなくなる。**

吐くのは「入力（形・材質・位置の列）」と「どの性質を縛るか（型紙）」だけ。
**録れた出力の数値は 1 つも入らない**（そのことを検査している）。

生成した実物は `AcousticEngineTest/generated_cases.inc` として**ビルドに入っている**。
★ここに置く意味は、生成器が「読めるコードらしきもの」ではなく
**実際にコンパイルが通って走るコード**を吐くことを担保すること。
実際、最初の版は `0` を `"0f"` と吐いていて**コンパイルが通らなかった**。

### 入力リプレイ ── どこまで一致するか（実測）

| 録った窓 | 帯域ゲイン | 尾（エコグラム） |
|---|---|---|
| 先頭から | 111/111 ビット一致 | 111/111 ビット一致 |
| 途中から（実用はこちら） | 91/91 ビット一致 | ⚠ **91/91 不一致・収束しない** |

★**原因**は段の間引きの位相。エコグラムはレイを 1/N ずつ撃って溜めるので、
**撃つフレームがずれるとその瞬間の扉の角度が違う**。
カウンタは録音側も再生側も 1 ずつ減るので、**ずれが永久に残る**。

★**直し方**: 位相をフレーム記録に入れて、押し直す前に戻す。

| | 位相を戻す前 | 戻したあと |
|---|---|---|
| 尾が一致しないフレーム | 91 / 91 | **6 / 91** |

⚠ 資料に「完全に一致します」と書いてはいけない。**6 フレームの暖機がある。**

### 実機で見つけたもの（`Test_Full` の 19 秒）

```
① 音源 11 で 14.7 dB の跳び ── f397 (4.93 秒)
② 閉扉の幻が 4 か所・合計 4.7 秒
     f0..188 (2.52s) / f200..277 / f294..345 / f430..491
```

②の生の値:

```
平均 -25.35 dB   遮蔽 0.95   傾き(低−高) 0.24 dB
0.0552 0.0541 0.0538 0.0537 0.0537 0.0537
```

★**-25 dB・遮蔽 0.95 なのに、5 オクターブで 0.24 dB しか傾いていない。**
壁の透過なら 21 dB 傾くはずで、物理的にありえない。

★①の跳びは②の幻の区間の**あいだ**にある（f345 と f430 の間）。
**幻に入る／出る境目で跳んでいる**という見立てが立った。

### 構成

| | 置き場所 | 役割 |
|---|---|---|
| 録る | `AcousticEngine/src/Debug/capture.h` | リングバッファ・入力・出力・PCM・形・材質 |
| 型紙 | `.../Debug/detectors.h` | 判定式（回帰テストと共用） |
| 走査 | `.../Debug/capture_scan.h` | 型紙を当てる |
| 吐き出し | `.../Debug/capture_emit.h` | 破れ → C++ の検査 |
| 録音 UI | `CaptureRecorder.cs`（F10） | 常時録音・印 |
| 閲覧 UI | `CapturePanel.cs`（F11） | 一覧・照合・印・PCM 再生・吐き出し |
| CLI | `AfCapScan.exe` | Unity 無しで走査・生の行を覗く |

⚠ エンジンは**録るだけ**で判定を持たない。判定を `AF_SceneUpdate` の経路へ入れると、
「あとから検出器を良くできる」という利点が消える。

## 2. AF ツール（Editor 窓・3 タブ）

### 一行

**鳴っている最中に、数字で追い、経路を切って耳で確かめる道具。**

### 履歴タブ ── 60 秒を巻き戻す

- 3600 フレーム（60fps で 60 秒）／音源 16 本まで
- 任意のフレームへカーソルを置いて、そのときの内訳を見る
  （出力の段別／RT60・部屋／回折 δ／主音源の 6 帯域／音源ごとの遮蔽）
- 閾値を指定して「跳び」に印

### 音源タブ ── ★経路を切って**耳で**確かめる

| | |
|---|---|
| 経路ゲート | `直接 D` `反射 R` `回折 F` `尾` を個別に on/off |
| ソロ / ミュート | 音源ごと |
| 並べ替え | **実出力**（実際に耳へ届く量＝マスキングの切り分け）／**経路ゲイン**（届きやすさ） |
| Scene に経路 | SceneView に描く |

★ここが AF ツール固有の値打ち。「この音、回折で来てる？ 透過？」を
**数字を見て推測するのではなく、消して確かめられる。**

★並べ替えの 2 基準を明示的に切り替えるようにしてある ──
「実際に届いている量」と「届きやすさ」は**別の問い**で、混ぜると読めなくなるため。

### 予算タブ ── audio thread の実費

- DSP ブロック（サンプル数 × バッファ数）／占有 %／音源ごとの実費
- 上限 **36 本**（★実測。1 スレッドが飽和するまで）

★**推定していない。**「0.292 ms × 本数」で見積もると実際と数倍ずれる ──
コストは本数ではなく**遮蔽された音源の数**で効くため。

## 3. 調整卓（TuningPanel / TuningWindow）

### 一行

**「この地点でこう聞こえてほしい」を置くと、それを担っている材質を逆算して書き換える道具。**

### なぜ「材質の数値」ではなく「聞こえ方」から入るのか

このエンジンの主題は「周辺環境の変化を音で伝える」こと。
だから調整の単位は**立っている場所での聞こえ方**であって、材質の数値ではない。
材質の表を睨んで 0.003 を 0.005 にする作業は、**耳から遠すぎて追い込めない**。

### 手順

```
① いま届いている音の内訳を出す（合成後 / 透過だけ / 回り込み）
② 透過が担っているなら、**誰が担っているか**をエンジンに名指しさせる
③ 「こう聞こえてほしい」を 2 つのつまみで置く（総量 dB / こもり倍率 125Hz÷4kHz）
④ 担い手の材質を書き換えて、その場で音が変わる
⑤ 届かない目標は**届かないと言う**
```

### ★書き込み先は必ず物理量（材質）にする

「この音源だけ EQ を掛ける」形にすると、**壁を動かしても補正が付いてこない**。
実行時に形状が変わる前提の音響エンジン、という位置づけが崩れて、ただのミキサーになる。
→ 入口は音源でも、**書くのは材質**。

### ★合うのは「その 1 点」だけ。それが狙い

材質は 1 枚で、聞く場所は無限にある。ある点で目標に合わせれば、
他の点はそこから**物理が決めた値**になる。
どこでも目標どおりに鳴るなら、それはベイクしたのと同じで、環境は何も語っていない。

> **代表の 1 点で演出を決め、残りは物理。**

### ★届かない目標は、届かないと言う

効かないつまみを回し続けるのが、この手の道具のいちばんの失敗。

```
⚠ この経路の 72% は回り込みが担っています。
   材質を触っても大きくは動きません。開口（戸口の幅）のほうが効きます。
⚠ もう素通しです。これ以上大きくはできません。
```

### ★担い手が複数のときは人が選ぶ

取り分が近いと、自動で選ぶ方式は触るたびに相手が入れ替わる。
「**勝手に何かが変わった**」がこの手の道具のいちばんの事故なので、一覧から選ばせる。

### 見た目は 2 つ、計算は 1 つ

| | ゲーム内 F9 | Editor 窓 |
|---|---|---|
| 動く場所 | **ビルドでも動く** | Editor だけ |
| 画面 | Game ビューを覆う | ドッキング。塞がない |

計算と書き込みは `TuningCore.cs` に**1 つだけ**置いてある。
見せ方が 2 つあるとき、写経すると必ずずれる。

## 4. 回帰テスト（土台）

### 数

| | 件数 | 何を守るか |
|---|---|---|
| Scene | **318** | 幾何・回折・透過・部屋・並列・段・キャプチャ |
| DSP | **117** | 畳み込み・HRTF・尾のバス・分割 |
| BTM | **7** | 回折の解析解との突き合わせ |

### ★期待値を「絶対値」でなく「関係」で書く

```
✗ フレーム 412 の 125Hz は 0.0837
○ 開口へ近づくほど大きくなる（向きだけを縛る）
○ 隙間を狭めるほど落ちる、かつ 12dB 以上動く（単調 かつ 効いている）
○ 並列にしても直列とビット一致する
```

絶対値を焼くと、**正当なチューニングのたびに落ちて、すぐ信用されなくなる**。
信用されない検査は、無い検査より悪い（落ちても誰も見なくなるので）。

### 実際にこれで助かった例

回折の「経路が消える」検査は、当初「ゲイン ≤ 1e-4 なら消えたとみなす」だった。
f が効くようになると、横へ外れた端が**正しく**小さくなって落ちた。
→ 絶対値をやめ、①経路が見つかること ②開口へ近づくほど大きくなること、の 2 つの関係へ。
**緩めたのではなく、見る物を変えた。**

## 5. 出荷事故を止める道具

★すべて「**実際に刺さった事故**」から作った。予防のために思いついたものは無い。

| 道具 | 止めるもの | 元になった事故 |
|---|---|---|
| `check_abi_parity.sh` | 構造体 4 つの**並び**・版番号・既定値・C# 宣言漏れ | `AF_VoiceTap` の並びずれで **Unity が数回ぶんビルド不能** |
| `check_csharp.ps1` | Unity を開かずに C# を型検査 | 通らない C# を「出来た」と報告 |
| `marshal_probe` | **P/Invoke のマーシャリング** | 走査の結果が空で返ってきた |
| DLL 鮮度チェック | 配り忘れた古い DLL で判断すること | 一日ぶん古いエンジンで音を聞いていた |

### ★検査そのものを検査している

`check_csharp.ps1` は一度**偽の合格**を出した。原因は 2 つ:

1. Unity は `Editor/` を**別アセンブリ**にするのに、1 つにまとめてコンパイルしていた
   → `internal` が見えて **CS0122 を 33 件素通し**
2. エラー判定が文字列一致で、**位置情報の付かないエラー**を取りこぼした
   → **失敗を成功と報告していた**

→ 2 段コンパイル＋終了コードで判定に直し、`-SelfTest` を足した:

```
[自己検査] わざと壊した入力で、ちゃんと落ちるか
  [OK] 別アセンブリの internal をちゃんと弾いた
  [OK] 文字列リテラルの生の改行をちゃんと弾いた
```

★型紙の自己検査とまったく同じ考え方。
**黙っているのが健全だからか、壊れて何も見ていないからか区別できない検査は、
無い方がまし。**

### ★型検査では捕まらないものがある

P/Invoke のマーシャリング属性は**型としては正しい**ので、型検査には出ない。
しかも間違っても例外は出ず、**値が 0 になる／文字列が空になる**だけ。

→ 実物の DLL を叩いて確かめる小道具を作った。同じエクスポートを 2 通りで宣言して差を見せる:

```
  属性なし  : frame=0  音源=0     型紙=「」
  [In,Out]  : frame=60 音源=9001  型紙=「型紙1 跳ばない」
```

## 6. 資料に載せるときの言い方（注意）

★**「プロファイラを作りました」は弱い。** 録音→再生→調整のループ自体は
FMOD Studio に既にある。**強いのはここ:**

1. **検出器が自分のエンジンで実際に出たバグから来ている**
   ── 「遮蔽されているのに帯域がまっすぐなら幻」は、汎用のプロファイラには書けない。
   **自分の模型の破れ方を知っている人しか書けない検出器。**
2. **空間エンジンとサウンドエンジンを跨いだ 1 つの記録**
   ── 既存は境界が会社をまたぐので単独で完結できない。ここは**自作の強み**。
3. **見つけた破れがそのまま回帰テストになる**
   ── しかも**絶対値でなく性質で縛る**。なぜそうしたかまで説明できる。
4. **道具そのものを検査している**
   ── 型紙も、C# の型検査も、「わざと壊した入力で落ちること」を確かめてある。

⚠ **盛らないこと。** 「常時リングバッファで録画開始を押さなくていい」は事実だが、
それ単体は小さい。**判断の質**を見せるほうが効く。

⚠ **書いてはいけないこと**（実測と違う）:
- 「入力リプレイは完全に一致します」→ **尾は 6 フレームの暖機がある**
- 「並列化しても結果は完全に同じ」→ **音源ごとの段はビット一致、エコグラムは相対差 4e-6**
- 「閉扉の幻は直っています」→ **未解決。実機で 4.7 秒ぶん出ている**
