## A1. C++ と C# の材質プリセットが食い違っている 【解消済み・★この節の推定は誤りだった】

> **2026-08-19 追記（`3b59d3c`）。**
> **「Unity で鳴っているのが C# だから C# が正」という下記の推定は間違いだった。**
> 正しくは **C++ が理由つきで上げられ、C# が置き去りになっていた**。
> `material.cpp` に「以前は 25/30/36/40/44/46 だった。壁が漏らしすぎると、扉から漏れる音が
> 壁の漏れに埋もれてどこから聞こえるか分からなくなる」という記録があり、
> **C# 側の値がまさにその『以前』の値**だった。
>
> こちらが誤読した原因は、`material.cpp` の冒頭コメントが**上げる前の説明のまま**
> 残っていたこと（システム側で修正済み）。**コメントを根拠に使うときは、
> 同じファイルのコードと突き合わせること**という教訓。
>
> 対応は `AF_MaterialPresetBands` を新設してエンジンを唯一の出どころにする形で入った。
> C# の旧表は引けなかったときの保険に降格。
> 以下は発見時の記録として残す（数字の並び自体は正しい）。

[material.cpp:2](../AcousticEngine/src/Core/material.cpp) に
「マテリアルのプリセット値。**C# 側 AcousticMaterial.cs と同値に保つこと**」とあるが、
**透過が一致していない**。

### 透過損失 TL[dB] = −10·log10(transmission)

| プリセット | 実装 | 125 | 250 | 500 | 1k | 2k | 4k |
|---|---|---|---|---|---|---|---|
| Default | C++ | 31.0 | 36.0 | 42.0 | 46.0 | 50.0 | 52.0 |
| Default | **C#** | **25.0** | **30.0** | **36.0** | **40.0** | **44.0** | **46.0** |
| | 差 | −6.0 | −6.0 | −6.0 | −6.0 | −6.0 | −6.0 |
| Concrete | C++ | 34.0 | 38.0 | 44.0 | 50.0 | 56.0 | 60.0 |
| Concrete | **C#** | **26.0** | **30.5** | **36.5** | **42.0** | **48.0** | **54.0** |
| | 差 | −8.0 | −7.5 | −7.5 | −8.0 | −8.0 | −6.0 |
| Glass | 両方 | 20.0 | 23.1 | 26.0 | 29.1 | 32.0 | 34.9 | ✓一致 |
| WoodDoor | 両方 | 15.0 | 18.0 | 21.0 | 24.0 | 26.0 | 27.0 | ✓一致 |

吸音率と散乱率は 4 プリセットとも一致。**ずれているのは Default と Concrete の透過だけ。**

### どちらが鳴っているか

ホストは `AcousticMaterial.FromPreset()`（C# 側）を作って `AF_SceneAddMaterial` へ渡す
（`AcousticFlowSceneDemo.ResolveMaterialId`）。**Unity で鳴っているのは C# の値。**

さらに `material.cpp` の冒頭コメントは「石膏ボード −18〜28dB級 / **コンクリ −26〜54dB級**」と
書いていて、これは **C# の値**（26.0〜54.0）の説明になっている。
同じファイルのコードが持つ値（34.0〜60.0）と食い違う。
両方を上げたが上げ先が揃わなかったように見える。

### なぜ問題か

決めごと #1「同じ問いに 2 つの答えを持たせない」そのもの。実害もある ──
**回帰テスト（C++）が守っている遮音量と、出荷する音（C#）が 6〜8 dB 違う。**
§9 の「エンジン既定とホスト設定が食い違うと、テストが出荷しない設定を守ることになる」
（`apertureContrast` で踏んだ事故）と同じ型。

### 直し方

値を片方へ寄せるだけでは、また同じことが起きる。**片方から生成するか、
どちらかを唯一の出どころにする**のが本筋。最低でも一致を回帰で縛れば再発は止まる。

## A2. 屋外で残響の「量」が幾何から決まっていない

`AcousticFlowSceneDemo.UpdateReverbTargetRatio` は、部屋が取れないとき
（`RoomVolumeAt` <= 1）にフォールバックへ落ちる。

```
V    = 全オクルーダーの bounds を Encapsulate した外形箱の体積
RT60 = _reverbDecay = エコグラムの「−60dB を超える最後のビン」
```

尾の**形**（エコグラム）は実際の幾何と材質から来ているので問題ない。
**問題は量**＝ `(r/rc)²`, `rc = 0.057√(V/RT60)` の V と RT60。

- **V が部屋ではない。** 草原（地面 90×90m）だと外接箱は約 28,000 m³
- **RT60 の測り方が §9 で名指しで禁じられているもの。**
  「RT60 を『−60dB を超える最後のビン』で測ってはいけない。エコグラムの窓に縛られて鈍い。
  吸音率が 17.6 倍違う 2 部屋を 0.50s と 0.51s としか区別できなかった」

### 影響

草案 §4.2 は「**屋外には部屋がない。尾も立たない**」と明言している。実装は逆に、
屋外でこそ根拠のない尾を作る。5 世界のうち **3 つが屋外**（草原・海・雪山）で、
神殿・洞窟も屋外から入る。

### 直し方の候補

- 部屋が取れないときは `target = 0`（尾を出さない）
- あるいは屋外用の別モデルを持つ（→ C3）

### ⚠ 未確認

**屋外の広い自由空間が部屋グラフで「巨大な 1 部屋」として検出される可能性がある。**
その場合はフォールバックに落ちず、巨大 V による尾が出る（症状は同じだが原因が違う）。
`OutdoorTailGate` の Inspector に `roomVolume` を出してあるので、実機で確認したい。

# B. 改善点

## B1. HRTF が直接音タップにしか掛からない ★

### 実装

[voice_renderer.h](../AcousticEngine/src/Dsp/voice_renderer.h) `renderChunk`:

```cpp
early_.processSample(dry, hrtfActive, l, r, scatSend, directMono);
if (hrtfActive) { hrtf_.processSample(directMono, dirL, dirR); l += dirL; r += dirR; }
```

- HRTF を通るのは `directMono` **だけ**
- [early_reflect_conv.h:107](../AcousticEngine/src/Dsp/early_reflect_conv.h)
  「**taps[0] は直接音であること**」より、`directMono` ＝ D タップ 1 本
- 回折（F）・反射（R）タップは `panL/panR` で `l, r` へ。
  そのパンはホスト側で「**前後・上下は中央＝HRTFは段3b**」と明記された等パワーパン
- 尾も HRTF を通らない（§4.7）。方向づけは `TailEarBandGain` の L/R バランスのみ

### なぜ「開口への定位が甘い」になるか

遮蔽されると D タップは材質の透過まで落ちる（§4.1 実測でコンクリなら 1e-4 級）。
**HRTF が掛かっているタップが、遮蔽時にはほぼ無音**になる。

実際に耳へ届いているエネルギーは F タップ ── 開口の方向を運んでいる側 ── で、
そちらは **L/R バランスだけ**。ITD なし・前後の区別なし・上下なし・
頭部のスペクトル手がかりなし。

洞窟ではさらに重なる。臨界距離 0.83m なので 1m 離れれば残響優位、その残響も
HRTF を通らない。**洞窟で聞こえているものはほぼ全部が L/R バランスだけの定位。**

### 影響

§4.3 の「回折が運ぶのは開口の方向」「音の方へ進むと穴に着く」は
**神殿と洞窟の主題そのもの**。ここが立たないとその 2 世界が成立しない。

### 直し方の候補

全タップを HRTF に通す必要はない。**いちばん強い F タップ 1 本を HRTF に載せる**だけで
体験は変わるはず。

- コストの目安: §6 の内訳より HRTF 1 本 0.047 ms/block。
  音源あたり 0.292 ms に対して **+16%**
- ⚠ §8 の却下案「ソフト遮蔽に回折の床を足す（二重計上で定位が壊れた）」とは**別物**。
  あれはエネルギーを足す話、こちらは**同じエネルギーの空間化を変えるだけ**
- 検証案: 遮蔽ありで F タップだけを鳴らし、方位を振ったときに ITD と前後の区別が
  出るかを DSP 回帰で見る

### なぜ §7 に無いのか

§4.7 が「直接音タップだけに掛かる」と**事実としては**書いているが、
未解決課題としては挙がっていない。ホラー用途では「壁の向こう・柱の陰」が中心動作なので、
事実ではなく課題として扱う価値があると思う。

# C. 欲しい点

## C1. ポータルを部屋グラフの開口から自動生成したい ★

### いまの状態

- **`portals_` は手で登録するリスト**（`AF_SceneAddPortal` / Unity 側は `AcousticPortal`）
- **部屋グラフは開口を自動検出していて**、`AF_SceneApertureInfo` が
  **面積・中心・法線・両側の部屋番号**を返す
- この 2 つは繋がっていない。フレネル帯域積分（§4.3）が使うのは `portals_` だけ

つまり「ここが開口である」という同じ事実を、**エンジンが自動で持っているのに
人間がもう一度置き直している**。決めごと #1 に触れる。

実害も出た。神殿・洞窟を作ったとき、ポータルを置き忘れた状態では
**§4.3 のフレネル帯域積分が一度も走っていなかった**。戸口はただの幾何の隙間として
一般の回折で処理されるだけで、「音が抜けてくる」音色にならない。
置き忘れても静かに劣化するだけで、気づく手段が無い。

### ⚠ ただし、手置きには理由があった

[AcousticPortal.cs](../UnityDemo/Assets/Scripts/AcousticFlow/AcousticPortal.cs) の冒頭に
経緯が書かれている ──「開口の測り方は『面のうちどこまでを積分するか』に答えが無く、
窓の置き方を 4 通り試して全部別の理由で失敗した（直線上＝壁に沈む／稜線上＝跳ぶ／
重心＝部屋の外を数える／複数面＝薄い板が見えない）。ポータルはその答えそのもので、
積分範囲＝この矩形になる」。

**この曖昧さは、部屋グラフの開口検出が入ったいま解けているのではないか**というのが提案。
§4.4 の実測では「壁に窓 1.0×1.0m だけ → 開口 1 個・**1.0m²＝窓の実寸**」と、
面積を実寸で当てている。中心と法線も出ている。積分範囲の候補としては十分に見える。

矩形の縦横比が要るなら、開口ボクセルの bounding box から取れるはず。

### 提案

- 部屋グラフの開口から `portals_` を自動生成する（手置きは上書き用に残す）
- 少なくとも「ポータルが 1 枚も無いのに部屋が 2 個以上ある」ときは警告を出したい

## C2. 任意の材質を面ごとに指定したい 【実装済み】

> **2026-08-19 追記: システム側で実装された。**
> `AcousticSurfaceMode` = `Preset` / `Adjusted`（`absorptionScale` と
> `transmissionLossOffsetDb`）/ `Custom`（`AcousticMaterial.FromBands` で α と TL[dB] を直指定）。
> ゲーム側は草原の草地 α0.30 と雪山の雪 α0.30〜0.92 に使い、当て木を 2 つ外した。
> 以下は提案時の記録。

### 詰まっている場所

[AcousticMaterial.cs](../UnityDemo/Assets/Scripts/AcousticFlow/AcousticMaterial.cs) の
コンストラクタは 6 帯域の配列を 3 本受け取る **public**。**任意の材質は作れる。**
`AcousticScene.AddMaterial()` も public。

詰まっているのは `AcousticSurface` が `AcousticMaterialPreset`（enum）しか公開していない点、
それだけ。`ResolveMaterialId` が `surf.Resolve()` を呼んでいるので、
`AcousticSurface` に「任意値モード」を足せば通る。

### なぜ欲しいか

B2 のとおり、雪（α 0.6〜0.9）が作れない。いまは早期反射を切って代用しているが、
物理ではなくスイッチなので世界が増えるほど破綻する。

### 私見: これは**ゲーム側で解ける可能性がある**

`AcousticSurface` は `AcousticFlow/` にあるので今回は触れなかったが、
やることは enum の横に配列を足すだけで、エンジンには一切触らない。
**優先して確認する価値がある**（これが通れば B2 が消える）。

- あるいは地面反射だけの early 中心のモデルを持つ

## C4. 音源の指向性が新 ABI に無い

`acoustic_scene.h` に `Directivity` が 1 つも無い。旧 ABI（`acoustic_engine.h`）には 5 箇所ある。
`source_directivity.cpp` は実装があるが
「`TODO(directivity): 数値はすべて暫定。聴感・文献で要調整`」で placeholder。

### ゲーム側で起きていること

プレイヤー自身のベルをリスナーと同じ位置に置けない。
`FollowTransform` のコメントが理由を書いている ──
残響比 `(r/rc)²` が r=0 で 0 になり尾が消える。物理的には正しいが、
現実に自分の音が響くのは指向性と耳の位置の非対称性によるもので、それが未実装。

**いまは 1.5m 前方に置いて誤魔化している。** 実害は小さいが、
「自分のベルが部屋を鳴らす」のは本作のコア体験なので、いずれ効いてくる。

## C5. 臨界距離 rc をゲーム側から読みたい

難易度は `rc = 0.057√(V/RT60)` で決まる（§7.1）のに、ゲーム側から読めるのは
`Status.RoomVolume` と `Status.RoomRt60`（500Hz 代表）だけで、rc は自前計算になる。

`Status.ReverbTargetRatio` はあるが、これは知覚圧縮後の値。

**私見: ゲーム側で計算すれば済む**ので優先度は低い。ただし

# 参考: §7.1 について

「残響が直接音を潰す」は体験上の最優先として §7 に載っているが、
ステージごとに数字を作ってみた結果 **材質を選べば避けられる**ことが確認できた。

| 世界 | 材質 | RT60 | 臨界距離 |
|---|---|---|---|
| 神殿 | Default (α0.208) | 約 1.4s | 約 2.6m |
| 洞窟 | Concrete (α0.038) | 約 5.1s | 約 0.83m |

神殿は「響くのに定位が立つ」、洞窟は「立たないことが難易度」。
**同じ数字が世界によって不具合にも設計にもなる**ので、
エンジン側で潰す種類の課題ではないと思う（決めごと #3「絶対値は演出で決める」）。
