# 開発ログ：技術を1つ入れるたびに起きた事故と、その直し方

作品制作の記録用。**「何を入れたか」より「入れたら何が起きて、どう聞こえて、なぜで、どう直したか」**を残す。
症状は全部“実際に耳で気づいたもの”から始まっている。

読み方：各項目は **症状（聞こえ方）→ 原因 → 直し方 → 学び** の順。

---

## A. Wwise 配線まわり

### A-1. 周波数別の遮蔽（3バンドEQ）を入れたが、音が変わらない
- **症状**：EQとRTPCを配線したのに、Play中に何をしても音色が変わらない。
- **原因**：2つ重なっていた。
  1. Wwise側で試聴するとき、Game Parameter の **Simulation Value が 0 のまま**だった（範囲の Min を -24 にしただけで、“今流している値”は 0）。
  2. Transport に載せていたのが **EQ を挿した対象と別のオブジェクト**だった（EQ は音楽の Actor-Mixer、鳴らしていたのは足音）。
- **直し方**：Simulation Value を -24 にし、**EQ を挿した対象そのもの**を Transport で鳴らして確認。ゲーム側は `useBandEq` を ON。
- **学び**：Wwise の不具合切り分けは **「値」「対象」「バンク再生成」の3点セット**。どれか1つ欠けると“無反応”になり、原因が見えない。RTPC名は大文字小文字まで厳密一致（`Occ_Low` 等）。バンクは **EQ を足した“後”に再生成**しないと反映されない。

### A-2. 壁で完全に遮蔽しているのに、音がしっかり聞こえる
- **症状**：壁を挟んで透過音だけのはずなのに、はっきり聞こえ続ける。「こもるけど、無音には程遠い」。
- **原因**：EQモードで**音量まで EQ に委ねていた**（Occlusion を 0 にした）。ところが Wwise Parametric EQ ＋ RTPC 範囲は **最大 -24dB で頭打ち**。どれだけ遮蔽しても -24dB 止まりで、-24dB は普通に聞こえる。
- **直し方**：根本的には **IR 畳み込み側で解決**した。畳み込みの直接タップは「材質の透過ゲインそのもの」なので上限が無く、コンクリなら -40dB 以下まで素直に落ちる。
- **学び**：**「音量」と「音色」を同じ機構に載せると、その機構の上限に縛られる**。分離するか、物理値をそのまま掛けられる経路（畳み込み）に移す。

### A-3. 足音が「すごく重なって」聞こえ、ループが壊れる
- **症状**：足音ループにすると、音が異常に重なって団子になり、リズムが崩壊する。
- **原因**：素材が **Wwise 側で Loop 済み（15秒）** なのに、コードは**ワンショット前提で 0.5 秒ごとに再トリガ**していた。→ 15秒ループの新インスタンスが 0.5 秒ごとに積み上がり、止まらない。
- **直し方**：`footstepEventLoops` を追加し、**Loop 素材のときは再トリガしない**（1回 Post して Wwise のループに任せる）。
- **学び**：**素材側の Loop 設定と、コード側の再生方式の前提を必ず一致させる**。「ワンショットをループ化する延命策」は、素材が既にループだと有害に反転する。

## B. IR 畳み込みの導入

### B-1. 段1：マルチタップ（離散IR）を入れた
- **聞こえ方の変化**：クリック音に反射が付き、**動くと反射パターンが変わる**。壁裏に回ると直接音が静かになり、**遮蔽が“勝手に正しく”なった**（A-2 の -24dB 天井が消えた）。
- **学び**：タップが少数の離散点なら、**重い FFT 畳み込みでなくマルチタップ・ディレイで正確かつ軽く**鳴らせる。「IR 畳み込み」は身構えるほど大げさではなく、まず離散タップで動く。

### B-2. 音楽（持続音）を通したら、濁って「うつろ」に聞こえる
- **症状**：クリックでは良かったのに、音楽を通すと「めっちゃ重なってる」「シュワシュワする」「元の音に聞こえない」。
- **原因**：**少数の強い離散反射が、持続音に対してコムフィルタ**（櫛状の山谷）を作る。トランジェント（クリック・足音）では“はっきりしたエコー”として自然に聞こえるが、持続音では**位相の櫛**として濁る。
- **直し方**：まず `reflectionLevel` で反射を絞って直接音を主役に。根本的には**密な後期尾を足す**方針へ（→ C 章）。
- **学び**：**スパースな IR は transient に強く sustained に弱い**。テスト信号をクリックだけにしていると、この弱点に気づけない。

### B-3. たまに音が出なくなる
- **症状**：時々、鳴らない瞬間がある。
- **原因**：タップが一瞬 0 個になったときに、**「空の IR」へクロスフェードして無音**になっていた。
- **直し方**：**空IRガード**（タップ 0 のときは前の IR を保持）。あわせて**連続ノイズのテスト信号**を追加し、「途切れ」を耳で判定できるようにした（クリックだと元々“無音の間”があるので判別できない）。
- **学び**：動的にデータを差し替える系は、**「データが無い瞬間」の保険**が必ず要る。また**症状を判定できるテスト信号**を用意しないと切り分けられない。

## C. 後期残響（今回いちばん時間を食った所）

### C-1. velvet noise の尾：ドラムで「ザラザラ」
- **症状**：後期残響を“密なランダムタップ”で作ったら、**打楽器で粒が聞こえる**（ザラザラ）。
- **原因**：固定 N 本のタップは**密度に上限**がある。ドラムのようなトランジェントは、その**タップ列をほぼそのまま“印字”**するので、個々の粒が聞こえてしまう。
- **途中の改善**：①ランダム配置 → **均等分散（velvet noise 本来の 1セル1パルス）** ②**密度アップ** ③**RMS正規化**。かなり滑らかになったが、打楽器では露呈が残った。
- **学び**：**「密度を近似で作る」には限界がある**。特に transient がそれを暴く。

### C-2. 部屋が広いほど残響が強すぎる
- **症状**：小部屋は良いのに、大部屋だと残響の存在感が過剰。
- **原因**：RT60 が長い＝減衰が遅い＝**多くのタップが大きいまま残る**＝総エネルギーが増える。
- **直し方**：**尾の RMS 正規化**。残響の“量”は一定に保ち、**部屋差は“尾の長さ”で表現**する。
- **学び**：**部屋の違いは「音量」ではなく「減衰時間」で出すのが自然**。物理的にも、大きい部屋の残響は“うるさい”のではなく“長い”。

### C-3. FDN に置き換えたら「びりびり」（金属的）
- **症状**：4本の FDN にしたら、**長い残響ほど「びりびり」**と金属的に鳴る。
- **原因**：**遅延線 4 本＝モード密度が低い**。少数の共鳴が長く鳴り続け、離散した音程感として露呈する（4本FDNが“メタリック”と言われる典型）。
- **直し方**：**8本 → 16本**（高速Walsh-Hadamard変換で混合）。モードが増えて残響がノイズ状に溶ける。
- **学び**：**FDN の本数＝モード密度＝滑らかさ**。長い残響ほど本数が要る。

### C-4. 16本でもまだ粒感がある
- **原因**：FDN の**立ち上がり（最初の数十ms）がまだ疎**。密度は再帰で増えるが、増えるまでに数周かかる。
- **直し方**：**入力ディフュージョン（allpass を 4 段直列）**。dry を FDN に入れる前に位相を撹拌し、**入り口から即座に密**にする。
- **学び**：Schroeder / Dattorro 系の定番構成＝**「撹拌してから回す」**。FDN 単体では入り口が粗い。

### C-5. 低音が「びりびり」／全体が「薄っぺらい」
- **原因**：**低域はモードが疎**で、しかも HF ダンピングのせいで**低域だけ長く残る**→ 少数の低域共鳴が唸る。
- **直し方**：**残響入力の低域カット（~150Hz）**。直接音の低音はそのまま残し、**残響にだけ低域を入れない**。
- **学び**：**残響の低域は積極的に切る**のが定番。低音の“体”は直接音が持てばよい。

### C-6. 開けた場所なのに残響が鳴る（※これはユーザー側の指摘で発覚）
- **症状**：密閉箱の外＝**リスナーの周りに壁が無い**のに、残響が聞こえる。
- **原因**：RT60 / wet が小さいときに「まだ計算されていない」とみなして **0.5秒 / wet 0.3 にフォールバック**していた。→ **開けた場所という“正しい 0”をデフォルト値が潰していた**。
- **直し方**：フォールバックを除去し、**実際の値を尊重**（0除算だけ回避）。開けた場所は無響、囲まれた部屋は残響、と場所で正しく変わるようになった。
- **学び**：**「安全のためのデフォルト値」が、物理的に正しい 0 を上書きしてしまうことがある**。フォールバックは“データが無い”と“値が小さい”を区別できないと害になる。

### C-7. 透過・回折が効いているように聞こえない
- **症状**：壁の向こうに音源があるのに、遮蔽している感じがしない。
- **原因**：**FDN 残響に“生の dry”を入れていた**。＝遮蔽と無関係にフル音量で残響が鳴り、**遮蔽をマスク**していた。
- **直し方**：**残響を音源の遮蔽レベル（透過ゲイン）で絞る**。壁の奥の音源は、部屋に入れるエネルギー自体が減るので残響も小さくなる。
- **学び**：**遮蔽は直接音だけの話ではない**。「その音源が空間に注げるエネルギー全体」に効く。片方だけ絞ると、もう片方がマスクして効果が消える。

### C-8. ドラムが軽い
- **原因**：残響・反射が良くなった分、**直接音のパンチが相対的に埋もれた**。
- **直し方**：`distanceRef` を上げて直接音を前に、`tailLevel` / `reflectionLevel` を下げる。
- **学び**：**D/R（直接:残響）バランスは最後に耳で決める**。ここから先はミックスの好みの領域で、コードの問題ではない。

## D. 経路を変えたら、前の層が担っていた責務が抜けた

### D-1. 距離で音量が変わらない
- **症状**：音源に近づいても遠ざかっても**音量が変わらない**。
- **原因**：エンジンのタップは**“相対”減衰のみ**で、**絶対的な距離減衰は Wwise の Attenuation が担当**していた。畳み込み経路は Wwise を通らないので、**その責務がまるごと抜け落ちた**。
- **直し方**：各タップに **1/r（経路長ベース）** の距離減衰を追加。
- **学び**：**レンダリング経路を差し替えると、前の層が黙って担っていた仕事が消える**。「何がどこで効いていたか」を洗い出してから移す。

### D-2. Wwise の音は畳み込めない（が、逆向きは可能）
- **わかったこと**：Wwise は自前のエンジンで出力するので、Unity の `OnAudioFilterRead` で **Wwise の出力を“掴む”ことはできない**。
- **一方で**：自分で作った音を **Wwise の Audio Input プラグインで“流し込む”ことはできる**。
- **学び**：**「畳み込みは自分側でやってから、完成した音をミドルウェアに渡す」**が正しい向き。これは最終ビジョン（ミドルウェア非依存）とも一致する。

## F. 後期残響を「合成」から「実測」へ（partitioned convolution 導入）

FDN（RT60 スカラから合成）をやめ、**エコグラムをそのまま尾の IR にして畳み込む**方式へ移行した回。
コンセプト（フル IR での計測・全動的）に対して、尾だけが合成だったのを揃える作業。

### F-1. そもそも「フル IR で計測」を名乗れていなかった
- **状況**：エンジンは `computeEchogram` で時間ビンごとのエネルギー＝**尾のエンベロープそのもの**を出していたのに、
  ホストはそこから **RT60 という 1 スカラだけ**を取り出し、FDN に食わせて尾を合成し直していた。
- **なぜそうなっていたか**：時間領域のマルチタップしか畳み込み機構が無く、**1 秒級の密な IR を鳴らす手段が無かった**。
  疎な近似（velvet noise）は C-1 の粒立ちで破れ、逃げ場が FDN だった。
- **学び**：**C 章で時間を食った本当の原因は「残響の音質」ではなく「畳み込みエンジンの不在」だった**。
  手段が無いと、測れているデータまで捨てて近似に逃げることになる。

### F-2. ブロック遅延は「尾の立ち上がり」に隠せる
- **懸念**：一様分割 overlap-save の固有遅延は 1 ブロック分。小さくすると分割数が増えて重い。
- **気づき**：畳み込むのは**後期尾だけ**で、尾はそもそも早期部より後から始まる。
  → **ブロック遅延を尾の開始時刻の中に隠せる**。2048 サンプル(≒43ms)でも遅れて聞こえない。
- **結果**：1 秒の尾が 24 パーティションで済み、「フル畳み込みは重すぎて無理」ではなくなった。
- **学び**：**レイテンシ要件は信号の性質で決まる**。「畳み込み＝低遅延必須」と決めつけると、不要に重い設計になる。

### F-3. 尾の IR は「固定ノイズ × 実測エンベロープ」
- **やったこと**：`尾IR(t) = ノイズ(t) × √(実測エネルギー包絡(t))`。1 本のノイズを 6 帯域に分け、各帯域の実測包絡で整形。
- **ノイズ系列は固定**：包絡が更新されるたびに引き直すと IR が毎回別物になり、差し替えでプチッと鳴る。
  系列を固定して**包絡だけ差し替える**と前後の IR が強く相関し、切替がほぼ聞こえない。
  尾はもともとノイズなので「どのノイズか」に音質上の意味は無い。
- **副産物**：帯域別の実測減衰がそのまま出るので、**「高域が先に減る」をダンピング係数で捏造しなくてよくなった**。

### F-4. 較正を 3 回外した（毎回“比”の意味を取り違えた）
尾の絶対レベルをどう決めるか、で連続して失敗した。**症状 → 誤診 → 実測で発覚**の記録。

1. **wet = tail/total を D/R 比として使った** → 実測比 24。
   `total-peak` は「最大ビン以外の全部」で、早期反射も全部“残響”に入る量だった。**D/R 比ではない**。
2. **エコグラムの尾/直接比を使った** → 3 桁ずれ。
   エコグラムは 1/r を含まない“相対の形”で、**直接(2m)と反射(数十〜数百m)で欠けている補正が違う**。
   単位が同じでも比は無意味だった。臨界距離で検算していれば書く前に気づけた。
3. **距離減衰を「総経路長」で掛けた** → 広い部屋の中央だけ反響が痩せた。
   時間が経つほど一律に減衰が強まり、**尾に本来ない 1/t² が乗る**。拡散音場のエネルギー密度は空間的にほぼ一様で、
   時間減衰は吸音だけが担うべき。正しくは**音源→反射点の区間にだけ**掛ける
   （反射点→リスナー側は、レイ 1 本が立体角を代表していること自体が担っている）。
- **最終形**：エコグラムは**尾の“形”専用**にし、**“量”は物理式**（残響/直接 = (r/r_c)²、r_c=0.057√(V/RT60)）で決める。
  V と RT60 から部屋ごとに正しい比が出るので、部屋を変えても一貫する。
- **学び**：**「比」は単位が揃っていても意味が揃っているとは限らない**。
  分子と分母で*欠けている補正*が違えば無意味。独立な物差し（臨界距離）で検算する癖をつける。

### F-5. 粒立ちを平滑で潰したら「広さ」が消えた（← 一番の反省）
- **症状**：大部屋で残響に粒立ち（ザラつき）。
- **正しい診断**：レイのバウンス数が足りず、**尾の後半に届くレイが激減**していた（8 バウンス＝292ms 分しか届かず、尾は 620ms）。
- **やってしまったこと**：原因を特定していながら、**3 回続けて「測定をぼかす」対処を重ねた**
  （空間平滑 → 時間比例平滑 → 時間平均）。粒は消えたが、**同時に「広さ」の手がかりも消えた**。
  ITDG・初期反射の並び・尾の立ち上がりの形はどれも平滑が真っ先に潰す。行き着く先は
  「なめらかな指数減衰」＝ FDN で、**コンセプトが否定したはずのものに戻っていた**。
- **直し方**：`echogramBounces` を 8→24（必要数 ≒ 尾の長さ×音速÷平均自由行程）。平滑は既定 0 付近に戻す。
  **推定量を足す方向は情報を増やすので、粒立ちと広さが両立する**。
- **学び**：**実測を名乗るシステムでは、平滑は最後の手段**。
  「症状が出る→手前で潰す」を繰り返すと、副作用が別の症状として出てまた潰す連鎖になる（C 章と同じ構造）。

### F-6. 早期反射が「窓」から漏れて消えていた
- **症状**：特大部屋（58m 級）で早期反射・散乱が**まるごと 0**。
- **原因**：壁が遠いと最初の反射が遅く届く（58m 部屋の側壁反射は 163ms）のに、
  早期窓が `maxIrMs=120ms` 固定だった。**遠壁の反射が全部窓の外に落ちていた**。
- **直し方**：早期↔後期の境目を **mixing time ≈ √V(ms)**（Polack の目安）に。窓長も 400ms へ拡張。
  境目は RT60 の定数倍では代用できない（√V と依存性が違い、小部屋と大部屋で逆に外れる）。
- **学び**：**時間窓の定数は「部屋の広さ」に対して不変ではない**。固定値は必ずどこかの規模で破綻する。

### F-7. 物理的に正しい残響量は、知覚的には正しくない
- **症状**：物理式で較正したのに、部屋を変えると残響の量が過剰に振れる。「現実はこんなに差が出ない」。
- **原因**：合わせている量（エネルギー比）が、**人が「残響の多さ」として聞いている量ではない**。
  - **先行音効果**：直接音とその直後（〜40ms）は融合し、**直接音側に強く重み付け**される。
    エネルギー的に残響が勝つ小部屋でも、耳は直接音を主として聞く。
  - 部屋の広さの手がかりは主に**減衰時間**であって音量比ではない（**C-2 で既に得ていた結論**）。
- **直し方**：物理比を指数で圧縮（`ratio^0.5`）。r=r_c を不動点にすると「臨界距離で直接=残響」は保たれ、
  そこから離れたときの振れ幅だけが穏やかになる。小/特大の開きが 530 倍→24 倍。
- **学び**：**物理的な正しさと知覚的な正しさは別物**。シミュレーションの出口には知覚モデルへの写像が要る。
  そして **C-2 で一度得た結論（部屋差は音量でなく減衰時間）を、物理式を入れたときに巻き戻していた**。
  過去の結論は、新しい理屈を入れるときに壊れていないか確認すること。

## G. 回折：厳密解（UTD）を実装してから、経験則（前川）に置き換えた

### G-1. 症状：歩くと回折音がブツブツ切れる

遮蔽の境目を跨いで歩くと、回り込みの音が滑らかに変化せず段差で切り替わった。
`AcousticEngineTest` に「影境界を横切る掃引」を追加して数値化したところ、
隣接 0.25m での最大差が **12.5dB** あった。耳で分かるはずである。

### G-2. 実は同じ根が 3 箇所にあった

原因は「**遮蔽を透過だけで測り、回折を勘定に入れていない**」こと。同じ誤りが独立に 3 箇所にあった。

| 箇所 | 症状 | 段差 |
|---|---|---|
| 回折ゲイン (`computeDirectSoft`) | 回り込み音が切り替わる | 12.5 dB |
| 残響ゲート (`SourceLevel`) | 遮蔽した瞬間に残響が消える | −35 dB |
| IR 直接タップ | 直接音が過剰に落ちる | −34 dB |

後ろ 2 つは「遮蔽＝透過率」で判定していたのを「透過 ⊕ 回折の大きい方」に直すだけで解決した
（−3.6dB / −12.9dB まで縮小）。**症状が 1 つに見えても、同じ思い込みが複数箇所に埋まっていることがある。**

### G-3. UTD を正しく重ね合わせようとして、3 回失敗した

残る回折ゲイン本体が難物だった。UTD (Kouyoumjian-Pathak) は実装済みで、
影境界で 0.5 に収束するよう遷移関数 F(X) も入っていた。にもかかわらず飛ぶ。
原因は**どの稜線が最短かが位置によって入れ替わり、そのたびに UTD が見る 3D 幾何
（入射角 φ'・回折角 φ・ウェッジ角 n・Keller コーン角 β0）が不連続に変わる**こと。

「物理的に正しそうな」修正を順に試して、いずれも悪化させた。

| 試したこと | 結果 | なぜ駄目だったか |
|---|---|---|
| 全稜線の複素場を加算 | 12.5 → **17.6 dB** | UTD は各稜線を「孤立した無限ウェッジ」として評価する。箱の 12 稜線すべてが「自分が回折源だ」と主張し、足すほど過大計上になる |
| 方向でクラスタ→エネルギー加算 | **全域で飽和** | 同じ物理経路の稜線が複数クラスタに分かれ、同じ経路を何度も足した |
| 回折点を可視範囲に制約した最小点へ | **変化なし（ビット単位で同一）** | 仮説が外れ。最適点は元々可視だった |

δ による重み付き平均という**平滑化**でようやく 3.8dB まで下がったが、これは
構造的な限界を誤魔化していただけだった。

### G-4. 転機：δ は連続だが、UTD の幾何は連続でない

デバッグ出力で支配稜線 1 本を追跡したところ、決定的な数字が出た。

```
x=1.50   δ=0.0042   UTDゲイン 0.739
x=1.75   δ=0.0000   UTDゲイン 0.320   ← 幾何は 4mm しか動いていないのに 2.3 倍
```

ここから 2 つ分かった。

1. **`margin = 0.15f` の稜線膨張が致命的だった**。回折点を実形状から 0.15m 外に置いていたため、
   UTD が見る影境界（x=1.74）と `occ` 判定の影境界（x=2.0）が **0.26m ずれていた**。
   UTD は「直接音が消える点」と「回折場が符号反転する点」の一致で連続になる仕組みなので、
   両者がずれるとその区間だけ壊れる。実際、異常区間は完全に一致していた。
2. より重要なこととして、**δ（迂回の余剰長）そのものは連続**である。
   複数候補の min を取っても、argmin が入れ替わるだけで値は飛ばない（min は連続性を保つ）。
   飛んでいたのは δ ではなく、**δ 以外に依存している部分**だった。

### G-5. 判断：δ だけの関数に置き換える（前川の式）

作品のコアは「周辺環境の変化を音で伝えること」であって、回折の厳密性ではない。
そこで音声経路を **前川の式** に置き換えた。フレネル数 N = 2δ/λ だけの経験式である。

- **δ のみに依存 → 連続性が構造的に保証される。** 平滑化も重み付けも不要。
- **符号付き δ**（影で正・境界で 0・照射側で負）にすると、境界で両側とも 5dB 減衰に収束して繋がる。
- **λ で割るので高域ほど強く減衰する** → 6 帯域ゲインをそのまま適用すれば、
  別途フィルタを足さずに「回折によるローパス」になる。

結果:

```
最大の隣接差   前川 0.040 (0.35dB)  /  UTD 0.599 (7.9dB)
```

**12.5dB → 0.35dB。** 実装は UTD より*短く*なった。

### G-6. 学び

- **厳密解が実用解とは限らない。** 商用実装（Wwise の回折角カーブ、Project Acoustics の
  オフライン波動解の焼き込み）が一様に経験則寄りなのには理由がある。
  リアルタイム音声で効くのは**正確さより連続性**で、不連続は「間違い」として明確に聞こえるが、
  数 dB のレベル誤差はまず気づかれない。
- **「何に依存しているか」を見る。** 3 回失敗したのは全部「UTD の合成方法」を疑ったからで、
  本当の問いは「**出力が連続に動く量だけで書けているか**」だった。
  δ が連続だと気づいた時点で答えは決まっていた。
- **平滑化で誤魔化していると気づくこと。** 重み付き平均で 3.8dB まで下げたが、
  あれは構造的欠陥に蓋をしていただけで、形状が複雑になれば再発した。F-5 と同じ轍
  （推定量の不足を平滑で隠す）を、別の顔で踏んでいた。
- **捨てずに比較用に残す。** UTD は `Core/utd.h` と `AF_SceneComputeDiffractionBandsUtd` として
  残し、回帰テストで前川版と並べて出力している。選択の根拠が数値のまま保守され、
  死にコードとして腐らない。

## H. メッシュ対応と、逆の答えを出したベンチマーク

### H-1. 形状と配置を分ければ、動的な形状変化が「配置の操作」になる

`Instance.geomId` に「将来の BLAS(メッシュ)識別用」というコメントが最初から入っていた。
その通りに、形状（BLAS＝`MeshGeometry`）と配置（インスタンス）を分けた。
TLAS（インスタンスの BVH）は既にあったので、**葉の判定 2 箇所を差し替えるだけ**で済んだ。

これで変化の大半が形状の再構築を伴わなくなる。移動・回転・スケール変化は transform 更新だけ、
追加・削除はインスタンスの増減だけ。構築が要るのは形状そのものを生成するときで、
それも 1 個ぶん（レベル全体の再計算は決して起きない）。

ローカル空間の取り方が効いた。**頂点を「ローカル AABB が単位箱 [-1,1]³」になるよう正規化**して
持つと、`Instance.obb`（中心・正規直交軸・halfExtents）が**そのまま local→world の変換**になり、
同時に**ワールド境界ボックス**も兼ねる。追加のデータを一切持たずに済む。

非一様スケールは当初「法線の逆転置が要るし t の意味が変わる」と考えて禁止しようとしたが、
**部屋の内寸を変える＝壁を非一様に伸ばす**ことなので、禁止すると主張の中核が成立しない。
実際には懸念が過大だった ── **ローカルのレイ方向を正規化しなければ t はワールド距離と一致**し、
法線は R·S⁻¹（軸ごとに 1/h を掛けるだけ）で済む。

### H-2. ベンチマークが逆の答えを出した

「メッシュはレイトレースが重いはず。忠実度 LOD（近くはメッシュ、遠くは箱）が要るだろう」
という前提で、箱の部屋とメッシュの部屋を比べた。最初の結果はこうだった。

```
箱 6 枚               3.7 ms
メッシュ 23040 三角形   0.6 ms   ← メッシュの方が 6 倍速い？
```

**メッシュの部屋が閉じていなかった。** 床を生成するコードが退化三角形を作っていて、
床と天井が無かった。レイが即座に逃げるのでバウンスが起きず、速いのは当たり前だった。

気づけたのは、比較の各行に**尾のエネルギー**を出すようにしたから。
閉じていれば尾が立ち、開いていれば立たない。**「同じ条件で比べているか」を数値で見張る列**を
足すまで、速度の数字だけを見て納得しかけていた。

直した結果:

```
                        時間      対 箱    尾エネルギー
箱 6 枚                 3.84 ms   1.0×     0.210
メッシュ    12 三角形    8.07 ms   2.1×     0.218
メッシュ   192 三角形   16.31 ms   4.2×     0.218
メッシュ  3072 三角形   20.11 ms   5.2×     0.218
メッシュ 27648 三角形   24.27 ms   6.3×     0.218
```

### H-3. 学び：予定していた最適化が、実は効かないと分かった

数字を正しく取ると、**当初の計画（三角形数を減らす LOD）はほぼ無意味**だと分かった。

- **三角形数はほとんど効かない**。12 → 27,648 は **2,300 倍**の三角形なのに時間は **3 倍**。BVH が対数で効いている
- **メッシュにするだけで 2× 払う**。12 三角形でも箱の 2 倍。インスタンスごとの変換と BVH 走査の固定費
- したがって効くのは「三角形を減らす」ではなく「**メッシュを使うか箱で済ますか**」の二値

`CollArea` を使った忠実度 LOD（メッシュ簡略化）は**保留**にした。複雑さの割に得るものが小さい。
残響は 4 フレームに 1 回なので実質 6ms/フレーム相当だが、これは緩変な処理なので
**ワーカースレッドへ逃がす方が筋がいい**（1 フレーム遅れても知覚できない）。

- **「重いはず」の直感は当てにならない**。BVH のような対数構造が入っていると、
  スケールの効き方が直感と逆になる。**最適化の前に測る**は毎回正しい。
- **比較の妥当性そのものを数値で見張る**。速度を比べるときは「同じ条件で走っているか」を
  示す列を必ず並べる。それが無いと、壊れたベンチの結果を信じてしまう。

## E. 全体を通しての学び

1. **数値で見ると切り分けが一瞬**。Status Monitor に「タップの遅延/ゲイン」「送出dB」「RT60/wet/遮蔽」を出したことで、「鳴らない」「効かない」の原因が推測でなく**観測**で決まるようになった。可視化への投資は毎回すぐ回収された。
2. **音の問題は“層”で切り分ける**。直接音 / 早期反射 / 後期残響 / バランス、のどれかを必ず特定してから触る。層を混ぜて触ると迷子になる。
3. **テスト信号を目的で使い分ける**。クリック＝反射パターンの確認に最適。連続ノイズ＝途切れの確認。実際の音楽＝コムフィルタや粒感の暴露。**クリックだけで検証していると、持続音の問題に気づけない**。
4. **検証には“それが起きるシーン”が要る**。透過・回折は、壁が挟まっていないシーンでは何も起きない。現象ごとの専用シーン（回折 / 透過 / 小部屋 / 大部屋）を作ってから、確認が一気に速くなった。
5. **差別化と commodity を分けて時間配分する**。動的な幾何・早期反射・遮蔽・回折（＝差別化）は比較的早く動いた。**時間を食ったのは後期残響の音質**で、これはどのゲームも算法リバーブで済ませる commodity な部分だった。**磨く価値と時間を見誤らないこと**。
6. **フォールバック値を疑う**。「安全のため」に入れた既定値が、物理的に正しい結果（無響＝0）を潰していた。
7. **プロトタイプは反復が安い場所で作る**。DSP を C# で試作したので、リバーブの微調整を十数回回せた。C++（DLL再ビルド＋Unity再起動）でやっていたら同じ試行回数は不可能だった。**固まってから移植する**のが正しい順序。
8. **「手段が無い」が「近似で誤魔化す」を生む**。畳み込みエンジンが無かったせいで、測れていた尾のデータを捨てて FDN 合成に逃げていた（F-1）。音質の問題に見えていたものが、実は**機構の欠落**だった。次に音質で詰まったら「そもそも鳴らす手段はあるか」を先に疑う。
9. **推定量の不足を平滑で隠さない**。ノイズが出たとき、手前でぼかすと「不要な分散」と一緒に「必要な情報」も消える（F-5）。**サンプルを増やす（情報を足す）方向は両立するが、平滑（情報を削る）方向は必ず何かを失う**。
10. **物理的な正しさ ≠ 知覚的な正しさ**。エネルギー比を物理どおりにしても、先行音効果のせいで聞こえ方は合わない（F-7）。シミュレーションの出口には**知覚側への写像**が要る。逆に、知覚に寄せた値を「物理が間違っている」と誤解しないこと。
11. **定数は「どの規模まで成立するか」を書いておく**。120ms の早期窓は普通の部屋では正しく、58m の空間で破綻した（F-6）。スケール依存の定数は、部屋の広さなどの物理量から導出できないか常に疑う。
12. **厳密解が実用解とは限らない**。UTD（厳密）より前川の式（経験則）の方が、リアルタイム音声では明確に優れていた（G-5）。**不連続は「間違い」として聞こえるが、数dBのレベル誤差はまず気づかれない**。正確さと連続性が競合したら連続性を取る。
13. **「どう合成するか」より「何に依存しているか」を見る**。回折で3回失敗したのは全部「UTDの合成方法」を疑ったからで、本当の問いは「**出力が連続に動く量だけで書けているか**」だった（G-4）。δ が連続だと気づいた時点で答えは決まっていた。**直したい性質（連続性）を、後段の平滑化ではなく入力の選び方で満たす**。
14. **比較の妥当性そのものを数値で見張る**。メッシュのベンチが「メッシュの方が6倍速い」と逆の答えを出した。部屋が閉じておらずレイが逃げていたため（H-2）。速度を比べるときは「同じ条件で走っているか」を示す列（このときは尾のエネルギー）を必ず並べる。無いと壊れたベンチを信じる。
15. **「重いはず」の直感は当てにならない**。三角形数を2,300倍にしても時間は3倍にしかならなかった（H-3）。BVHのような対数構造が入ると効き方が直感と逆になる。**予定していた最適化が、測ったら無意味だった**ということが起きる。
16. **却下した実装は比較用に残す**。UTD は API と回帰テストに残し、採用版と並べて数値を出している（G-6）。**根拠が保守されるので、死にコードとして腐らない**。
17. **過去の結論が新機能で巻き戻る**。C-2 で「部屋差は音量でなく減衰時間」と結論したのに、物理式較正を入れたときに音量差を再導入していた（F-7）。**新しい理屈を足すときは、それが過去の決定を壊していないか確認する**。DEV_LOG はそのための資産でもある。
