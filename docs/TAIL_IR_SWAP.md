# 尾の IR を差し替えるときの人工物（不具合 #3、2026-09-08）

## 何を解くか
後期残響の尾は「実測エコグラムから組んだ密な IR」を分割畳み込みで鳴らしている。部屋が変われば IR も変わるので、**IR の差し替え**が起きる。
ホストは部屋が変わらなくても **8 フレームに 1 回**組み直すので、差し替えは常時起きている。ここに人工物があると、それは常時鳴り続ける。

測ってあった数字は 2 つだった（どちらも 2〜3 dB 級で、どちらを採るか決まっていなかった）:
- 即差し替え（器 1 つ）: **+1.97 dB** のふくらみが 0.35 秒。
- 並走クロスフェード（器 2 つ）: **−3.26 dB** の凹み。

## 分かったこと（原因が 2 つに割れた）

### ① 凹みの原因 ── 器を 2 つ並べたこと（直した）
分割畳み込み器は**周波数領域遅延線(FDL)**を持つ。中身は「過去の入力ブロックの FFT」で、**IR とは無関係**。
器を 2 つ並べて交互に使うと、休んでいる側の FDL は**止まったまま**になる。役割を入れ替えた瞬間、新しい側は過去の入力を持たない（初回）か、**前回休みに入ったときの古い入力**を持ったまま鳴り出す。だからフェードイン中の新側が痩せる。

→ **器を 2 つにするのが間違い。FDL は 1 本のまま、IR スペクトルだけ 2 世代持って混ぜる**（`partitioned_convolver.h`）。
新旧どちらも過去の入力を全部持ったまま鳴るので、凹みも膨らみも原理的に起きない。混ぜる重みは**等振幅**（新旧は同じ入力を同じエネルギーの IR に通した相関のある信号なので、等パワーだと混合中に +3 dB 膨らむ）。

```cpp
// 差し替え時（オーディオスレッド、ブロック境界）: いま鳴っている世代を「古い側」へ回すだけ。
//   遅延線 fdlRe_/fdlIm_ は触らない ── 共有だから新側も過去の入力を全部持っている。
drop = fading_;  fading_ = live_;  fadingParts_ = activeParts_;
xfadeSpan_ = xlen;  xfadePos_ = 0;  xfading_ = true;
live_ = p;
...
convolveInto_(live_, activeParts_, outBuf_);                       // 新しい世代
if (xfading_ && fading_) convolveInto_(fading_, fadingParts_, outBufOld_);  // 古い世代（フェード中だけ）
// 出力（サンプルごと、等振幅）
outCh[c][i] += (outBuf_[k] * wNew + outBufOld_[k] * wOld) * gain;
```

### ② ふくらみの原因 ── 段ごとの取り込み遅れ（クロスフェードでは直らない）
クロスフェードを 0 → 100 ms まで振っても、部屋を移るときのふくらみは **1.97 → 1.86 dB** としか動かなかった。段差ではなかった。
非一様分割は段ごとにブロックの大きさが違い（64 〜 8192）、**IR の後ろの方を担う段ほど取り込みが遅い**（最大ブロック 8192 = 170 ms）。
その間だけ「頭は新しい部屋・尾の後ろは古い部屋」になる。尾 IR はどちらもエネルギー 1 に正規化されているので、**合計が増える**。

確かめ: 最大ブロックを 8192 → 1024 にすると **+1.95 → +0.38 dB**。原因はこれで確定。
既定は変えない（分割数が増えて音声スレッドが重くなる。1.95 dB は 0.35 秒で収まり、しかもホストは `envAlpha` で包絡を滑らかに動かすので、実運用ではここまで跳ばない）。**残す不具合として記録する。**

## 数字（`tools/dev.ps1 test dsp`）

| 測るもの | 旧（器 2 つ） | 新（世代を混ぜる） |
|---|---|---|
| 同じ内容で差し替え、混ぜ 20 ms | **−14.92 dB** | +0.27 dB |
| 同じ内容で差し替え、混ぜ 50 ms | **−7.99 dB** | +0.27 dB |
| 部屋を移る、混ぜ 50 ms | −5.42 dB | +1.95 dB（②。最大ブロック 1024 なら +0.38） |
| 同じ IR を 8 ブロックごとに入れ直す（＝ホストの周期）、混ぜ 60 ms。入れ直さない対照との最大差 | **+8.0 dB**（尾の RMS より大きい＝別物） | **−128.6 dB**（一致） |
| 同じ IR を入れ直す、即差し替え | −212.1 dB（一致） | −212.1 dB（一致） |
| 尾の畳み込み 1 音源（1 s、全部入り） | 0.584 ms / 4 kHz 換算 5.47% | **0.435 ms / 4.07%** |
| 音源 8 本を個別に畳む 1 ブロック | 2.743 ms | **2.336 ms** |

★ **出荷側で鳴っていた**: ホストの共有バスは `TailBusRenderer.crossfadeMs = 60`（既定）で、旧実装ではこの経路が毎回の組み直しで器を入れ替えていた。つまり **8 フレームに 1 回、尾が別物に化けていた**（対照との差 +8.0 dB）。単体の音源側は既定 0 だったので、こちらは②のふくらみだけだった。

費用が下がったのは、器が 1 つになって遅延線が半分になったぶん（キャッシュ）。フェード中だけ掛け算と逆 FFT が 2 倍になるが、入力 FFT は 1 回のまま。

## 退けた書き方
| 案 | なぜ退けたか |
|---|---|
| 古い器の FDL を新しい器へ**複製**する（コード内に書いてあった案） | 1 音源あたり数百 KB の複製をオーディオスレッドか、スレッド跨ぎの受け渡しでやることになる。世代を混ぜれば**複製そのものが要らない**（遅延線は元から 1 本でよい） |
| 両方の器を常に回して FDL を揃えておく | 畳み込みが常時 2 倍。フェードしていない間もずっと払う |
| 等パワーのクロスフェード | 新旧は相関のある信号なので混合中に +3 dB 膨らむ。等振幅が正しい |
| ②を最大ブロックの縮小で直す | 分割数が増えて音声スレッドが重くなる。1.95 dB / 0.35 秒 は残す判断（実運用では包絡が滑らかなのでさらに小さい） |
| ②をクロスフェードで直す | 段差ではないので効かない（0 → 100 ms で 1.97 → 1.86 dB）。実測で確かめた |

## 壊れる所
- **尾の差し替えの聞こえ方が変わる**（共有バスを使っている場合は大きく変わる。今まで化けていたので）。**試聴で確かめる所。**
- フェード中だけ、その音源（またはバス）の尾の掛け算と逆 FFT が 2 倍。組み直しは 8 フレームに 1 回なので、50 ms のフェードは 133 ms のうち 50 ms を占める。気になるなら短くする。
- フェード中にさらに新しい IR が来ると、進行中の混ぜは打ち切られる（世代は 2 つまで）。組み直しの周期（133 ms）より長いフェードを入れると毎回打ち切りになる。**フェードは組み直しの周期より短く。**
- 部屋を移るときの +1.95 dB（②）は残っている。段の取り込み遅れなので、直すなら最大ブロックを縮める（費用と引き換え）。
- 器が 1 つになったので、`VoiceRenderer` の尾のメモリは半分。`TailBus` も半分。

## 口
- C: `AF_VoiceSetTailCrossfadeMs(voice, ms)`（新規。既定 50、0 で即差し替え＝ A/B 用）／`AF_TailBusSetCrossfadeMs`（既存、意味は同じ）。**ABI は変えていない**（構造体は増えていない）。
- ホスト: `VoiceConvolver.tailCrossfadeMs`（既定 50）／`TailBusRenderer.crossfadeMs`（既定 60、変更なし）。
- 検査: `[尾] IR を差し替えた瞬間の人工物`（長さを振る＋最大ブロックの切り分け）と `[尾] 同じ IR を入れ直し続けても尾が動かない`（対照と一致するか）。

# 追記（2026-09-08 夜）: 扉を動かすとぷつぷつ鳴る ── 本当の原因は尾の**量**の段差だった

## 経緯
Unity で試聴した発注者から「扉を動かすごとにぷつぷつと音の飛びが出る」。HUD の音声スレッド負荷は 10% 未満だったので**ドロップアウトではない**。
上の IR 差し替えの修正が効くと踏んだが、**外れていた**。再現の場を回帰に作って測ったら別の所だった。

## 再現の作り方（回帰 `[扉]`、`AF_ONLY=door`）
シーン（Test_SwingDoor と同じ形）→ タップの組み立て（DLL）→ 音源レンダリング まで通し、
**隣り合うサンプルの最大差 ÷ そのブロックの RMS**（＝段差）を測る。扉を止めた状態を平常とし、動かしたときの最悪値と比べる。

★**信号は正弦（220 Hz）にすること。** 最初は白色雑音で測って「出ない」と結論しかけた。雑音は元々サンプル間の差が大きく（段差の平常値が 4 前後）、クリックがその中に埋もれる。正弦なら平常値は 0.04 なので、切れていれば一目で分かる。実際に鳴らしているのは楽音や環境音なので、正弦の方が実機に近い。

| 信号 | 扉を止め | 扉を動かす |
|---|---|---|
| 白色雑音 | 1.31 倍 | 1.46 倍（**見えない**） |
| 正弦 220 Hz | 1.03 倍 | **15.21 倍**（面の線）／19.18 倍（像源レイ） |

## 切り分け（成分ごとに落として測る）
| 残した物 | 段差 |
|---|---|
| 全部 | 15.21 倍 |
| 尾を落とす | 1.17 倍 |
| 直接だけ | 1.15 倍 |
| 直接＋反射 | 1.18 倍 |
| 直接＋回折 | 1.24 倍 |
| **尾だけ（直接は残す）** | **51.82 倍** |

尾だった。さらに尾の中を割る:

| 尾の扱い | 段差 |
|---|---|
| そのまま | 51.82 倍 |
| **尾の量（directGain と目標比）を固定** | **1.03 倍** |
| IR を最初に 1 回だけ組む | 1.13 倍 |

→ **原因は IR の中身ではなく、尾の絶対レベル `tailGain_` の段差。**

## 何が起きていたか
`tailGain_ = calibrateGain(directGain, targetRatio)` は**組み直しのときだけ**動く（ホストは 8 フレームに 1 回＝ 85 ms）。
それをチャンクの間ずっと定数として掛けていたので、値が変わった瞬間に**波形が段になる**。
扉が動くと直接音のゲインも尾の比も速く動くので、85 ms ごとに段が出る ＝ ぷつぷつ。
タップ側は 30 ms で補間していたのに、尾の量だけ繋いでいなかった。

## 直し方
量を**チャンク内で線形に渡す**（タップと同じ考え方。量は必ず時間方向に繋ぐ）。

```cpp
const float tgEnd   = tailGain_ * lvl;      // 今回の目標
const float tgStart = tailAppliedGain_;     // 前のチャンクの終わりで実際に掛けた値
tailAppliedGain_ = tgEnd;
// 掛けるのは**入力側**。共有バスは全音源を足してから畳むので入力側でしか掛けられない。
for (int i = 0; i < n; ++i) { tailIn_[i] = input[i] * g; g += step; }
tailConv_.processAdd(tailIn_.data(), 0, n, dst, 0, 1.0f);
```

★出力側に掛けると、量が動いている間だけ共有バスと結果が食い違う（回帰 `[尾②]`「バスに差しても出力が変わらない」が −8.1 dB でこれを捕まえた）。**入力側に揃える**のが正しい。
`tailSrcLevel_`（部屋への注入量）の変化も、掛けた後の値を持ち越しているので一緒に飲む。

## 数字（回帰 `[扉]`、正弦・扉を動かす）
| | 直す前 | 直した後 |
|---|---|---|
| 面の線・尾の混ぜ 50 ms（既定） | 15.21 倍 | **2.09 倍** |
| 像源レイ・尾の混ぜ 50 ms | 19.18 倍 | **1.67 倍** |
| 面の線・尾の混ぜ 0 ms | 15.24 倍 | 16.79 倍 |
| 尾だけ | 51.82 倍 | 2.06 倍 |

★**混ぜ 0 の行が要点**: 量の傾斜だけでは直らない（16.79 倍のまま）。IR の差し替えの混ぜ（上の修正）と**両方**要る。片方だけでは残る。

## 残る所
- 既定でも 2.09 倍（平常 1.03）。残りは IR の中身が 8 フレームごとに変わること自体（1 回だけ組めば 1.13 倍）。クリックとしては聞こえない水準だが 0 ではない。減らすなら混ぜを長くする（費用と引き換え）。
- 白色雑音では測れない。この節の信号を雑音に戻さないこと。
