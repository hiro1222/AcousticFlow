# サウンドデバッグツール ── 形式の仕様

2026-08-23。元の設計メモ（`sound-debug-tool-design.md`）を、**この作品の実態に合わせて**
固めたもの。位置づけは **「おかしい所を探す道具」**であって、調整の道具ではない
（調整は別系統。`TuningPanel.cs`）。

---

## 0. この道具が何であるか（一行）

**常時録音した「入力」と「音響の出力」を、あとから走査して破れを見つけ、
そこから回帰テストを生やす道具。**

---

## 1. なぜこの形なのか（設計判断を先に書く）

元の設計メモは Wwise 型のミドルウェアを想定していた。この作品には
sound id / バス / RTPC / **ボイス管理（優先度・スティール・上限）** が無い。
なので §3 の検知項目のうち 4 つは**観測する対象そのものが存在しない**。
ここを写経すると「中身が空の機能」が並ぶので、作り直した。

### 判断1: 録るのは「結果の再合成用ログ」ではなく **「入力」**

エンジンは毎フレーム、ホストから
`リスナー / 音源位置 / 動いた実体 / Update` を押されて動く。
**その押している値を録って押し直せば、それが再現になる。**

- イベントログからの再合成（元メモ §6 シミュレートモード）が要らない
- RNG の結果もスティール記録も要らない（そもそも無い）
- **音源の情報は最初から全部見える**。実行中と同じ経路を通るので
- 容量は音源 16 本 × 60fps × 25 秒で **1MB 未満**

⚠ 代わりに「エンジンを直す前と後」は入力リプレイでは比べられない。
そこは**マスターPCM（録れた音そのもの）と並べる**ことで代替する。

### 判断2: 検知は**録音後の走査**にする（実時間の警告にしない）

- オーディオスレッドで判定しない ＝ 確保もロックも要らない
- ★**検出器を後で良くしたら、昔のキャプチャに付け直せる。**
  実時間だと録った瞬間の判定で固定される。**「跳びの判定はあとで」が設計の借金にならない**

### 判断3: 検出器は**この作品で実際に出たバグ**から作る

クリッピングや LUFS は入れてよいが優先度は下。**第一制約は連続性**なので、
跳びの検出が本命になる。詳細は §4。

## 2. キャプチャの中身

**プリロール 21 秒 / ポストロール 5 秒。**

⚠ 21 秒なのは、**畳み込み器の遅延線が冷えている**ぶんを捨てるため。
T-21s から流して T-20s から見せる。器の内部状態（過去 1 秒ぶんの変換済み入力）を
保存する代わりに、1 秒余分に録って暖める。

| | 中身 | 概算 |
|---|---|---|
| (a) ヘッダ | ASCII。版・並び・設定・材質表・シーン識別 | 数 KB |
| (b) フレーム記録 | 入力＋音響の出力（下表） | 約 1.5 MB |
| (c) マスターPCM | 48kHz stereo int16 | 約 5 MB |

**合計 6〜7 MB。**単一ファイル `.afcap`。

### 2.1 ヘッダは ASCII で、自己記述にする

```
AFCAP 1
sampleRate 48000
frames 1560
sources 16
fieldsGlobal frame,audioSample,lx,ly,lz,lqx,lqy,lqz,lqw,movedCount
fieldsSource sx,sy,sz,b125,b250,b500,b1k,b2k,b4k,dx,dy,dz,pathLen,tailLvl,taps
fieldsDiag   delta,useF,bounded,uFrac,vFrac
workerThreads 1
role1EveryN 1 role2EveryN 4 earlyEveryN 3 diffSrcEveryN 2 catalogEveryN 3
scene Test_SwingDoor  geomHash 8f3a91c2
engineAbi 5  dllHash 3d276c77
```

★**自己記述にする理由**: 版が変わると並びが変わる。ヘッダに並びが書いてあれば、
**古いキャプチャも読める**。今日、DLL の配り忘れで一日ぶん古いエンジンで音を聞いていた。
このプロジェクトは「古い物を掴んだまま気づかない」に弱いので、**識別子は全部ヘッダに焼く**
（`geomHash` / `dllHash` / `engineAbi`）。開いたときに現物と違えば**赤く言う**。

### 2.2 フレーム記録

**フレーム単位で進める。実時間で進めてはいけない。**
段の更新はフレーム数で間引いている（`role2EveryN` 等）ので、再生時の fps が違うと
**段の位相がずれて値が変わる**。録ったフレーム境界をそのまま辿る。

| 種別 | 中身 | 用途 |
|---|---|---|
| 全体 | フレーム番号 / オーディオクロック（サンプル数） | 時刻の唯一の基準 |
| 全体 | リスナーの位置・回転 | 再現 |
| 全体 | 動いた実体の transform（扉など。数は可変） | 再現。**動くのは扉だけ**なので軽い |
| 音源 | 位置 / 再生カーソル / 開始・停止 | 再現 |
| 音源 | **生存 6 帯域 / 到来方向 / 経路長 / 尾の量 / タップ数** | **走査（跳びの検出）** |
| 音源 | 〔任意〕δ / f使用 / 有界 / 縁 u,v | **原因の特定** |

⚠ **診断の列は `workerThreads = 1` でしか信用できない。**
診断カウンタはスレッドごとに持っている（競合を消すため）。並列だと呼び出し元スレッドが
担当した音源のぶんしか読めない。→ **デバッグ用の録音は直列で録る。**
⚠ ただし直列と並列では音響値がビット一致しない。
**「直列で録ったキャプチャ」と「並列で動く本番」は厳密には別物**である、と自覚しておく。

### 2.3 録らないもの

**音源ごとの個別 PCM。**48kHz stereo f32 = 384KB/s/voice、16 本 × 25 秒で約 150MB。
個別の音が要るなら**入力リプレイでソロにして鳴らし直す**（実行中と同じ経路なので可能）。

## 3. 再生

| モード | 何が鳴るか | いつ使うか |
|---|---|---|
| **波形** | 録れたマスターPCM | 「実際に何が聞こえたか」の物証。エンジンを直しても変わらない |
| **入力リプレイ** | 録った入力を押し直して**いまのエンジン**が解く | 音源の情報が全部見える。ソロ・ミュート・音量を触れる |

**この 2 つの A/B が、そのまま「直る前／直った後」になる。**

### 3.1 ⚠ リプレイはどこまで一致するか（実測・2026-08-24）

**以前ここに「同じビルドなら完全に一致する」と書いていたが、書きすぎだった。**
実際に押し直して測った結果:

| 録った窓 | 帯域ゲイン | 尾（エコグラム） |
|---|---|---|
| 先頭（フレーム 0）から | **111/111 ビット一致** | **111/111 ビット一致** |
| 途中から（リングが一周） | **91/91 ビット一致** | ⚠ **91/91 不一致・最大 15.5% ずれ。しかも収束しない** |

★**原因**: 段の間引きの位相。エコグラムはレイを 1/N ずつ撃って溜めるので、
**撃つフレームがずれるとその瞬間の扉の角度が違い**、出てくる尾が違う。
カウンタは録音側も再生側も 1 ずつ減るので、**位相のずれは永久に残る**
（扉が動き続けるかぎり一致しない）。

★**直し方**: 位相をフレーム記録に入れて、押し直す前に戻す（`AF_SceneDebugSetStagePhase`）。

| | 位相を戻す前 | 戻したあと |
|---|---|---|
| 尾が一致しないフレーム | 91 / 91 | **6 / 91** |

残る 6 フレームは**溜まりかけのエコグラムの中身**（位相は合っても中身までは戻していない）。
1 周＝ `role2EveryN` フレームで流れる。→ **窓の先頭 6 フレームぶんは信用しない。**

⚠ これは §2 の「21 秒録って 20 秒見せる」（畳み込み器の遅延線を暖める）とは**別の暖機**。
畳み込み器は 1 秒、段の位相は 6 フレーム。**両方要る。**

エンジンを直せば当然変わる ── それが見たいものなので正しい。

## 4. 検出器（録音後に走査）

★**この一覧が、この道具のいちばんの中身。**
汎用のプロファイラが持つ項目ではなく、**このエンジンで実際に出たバグ**から作る。

| 検出 | 破れの形 | 元になった実際のバグ（2026-08-23） |
|---|---|---|
| **跳び** | 隣接フレーム/位置で 6dB 超 | 閉扉で 23.0dB・19.7dB |
| **幻の経路** | 遮蔽されているのに**帯域がまっすぐ**（低−高 ≈ 0） | 閉扉の幻。回折も透過も周波数依存なので、平らなら模型が破れている |
| **比の破れ** | 尾と直接音の比が想定から外れる | 尾が 8.3 倍大きかった（`outputGain` の掛け忘れ） |
| **経路の消失** | 聞こえるはずの場所で経路が 0 本 | 2 次回折が 0.486→0.000 |
| **飽和** | f が全帯域 1.0 に張り付く | 開口率が 1.000 のまま（隙間幅が効かない） |
| **非決定** | 同じ入力で 2 回走らせて値が違う | 並列化で BVH が競合 |
| 〔下位〕 | クリッピング / LUFS 逸脱 | 汎用。優先度は下 |

### 4.1 閾値の注意

**素朴な隣接差だと毎フレーム光る。**段の更新間隔が違うので、
値は**正常でも規則的に階段になる**（エコグラム 4 / 早期反射 3 / 二次音源 2 フレーム）。

→ 段の周期を跨いで比べるか、**正常な階段より上に閾値を置く**。
実際の本物は 19.7dB と 23.0dB だったので **6dB** が妥当。

### 4.2 印には「何が動いたか」を持たせる

時刻だけでは、そこから手で追うことになる。

```
t=12.3s  音源3  125Hz が 19.7dB 跳んだ
         f使用 ○→×  ／  有界 1→0  ／  縁u 0.41→0.73
```

★今日この 3 つが並んで初めて「**有界判定が二値だから**」と特定できた。
**時刻だけの印なら特定できていない。**

## 5. 回帰テストの生成

★**絶対値を焼いてはいけない。**

このリポジトリの方針は「期待値を**絶対値でなく関係**で書く」
（`scene_regression.cpp` 冒頭）。フレーム 412 の 0.0837 を焼くと、
**正当なチューニングのたびに落ちて、すぐ信用されなくなる。**

```
キャプチャ → 変な区間を選ぶ → **どの性質が破れたか**を選ぶ
          → その性質を、録った位置の列に対して縛る C++ ケースを吐く
```

### 5.1 型紙 ── 9 つ。実装は `AcousticEngineTest/detectors.h`

★**走査（この道具）と回帰テストが同じ関数を呼ぶ。**別々の式にすると
「道具は見つけたのに検査は通る」「検査は落ちるのに道具は黙る」が起きる。

| # | 型紙 | 縛るもの | 元になった実際のバグ | 繋いだ検査 |
|---|---|---|---|---|
| 1 | 跳ばない | 隣接差が閾値以内 | 閉扉で 23.0 / 19.7 dB | `[閉扉] 距離掃引` |
| 2 | 向きが正しい | 掃くと単調に動く | 開口へ近づくのに小さくなる | `[開口率] 隙間幅掃引` |
| 3 | 経路が消えない | どこでも見つかる | 2 次回折 0.486 → 0.000 | `[回折のみ] 横掃引` |
| 4 | 幻が出ない | 遮蔽されているのに帯域がまっすぐ、が無い | 閉扉の幻（低−高 ≈ 0） | `[閉扉] 距離掃引` |
| 5 | 決定的 | 同じ入力で 2 回走らせて一致 | 並列で BVH が競合 | `[複数コア] エコグラム` |
| A | 比が保たれる | 2 つの量の比が範囲内 | 尾だけ **8.3 倍**（`outputGain` 掛け忘れ） | `[尾②] バス等価` |
| B | 設定不変 ★ | 速くするだけの設定で音が変わらない | 並列／共有バス／エコグラム分割 | `[複数コア]` ×3 |
| C | 効いている | 掃引の振れ幅がある | 隙間幅が効かない（2m でも 3cm でも同じ） | `[開口率] 隙間幅掃引` |
| D | 上限を超えない | 振幅比が 1.0 以下 | タップ 0.88 → **1.76** | `[開口率] 隙間幅掃引` |

**★2 と C は対で使う。** 単調性だけでは**定数が合格する**
（＝隙間幅が全く効かなかった当時のコードが通っていた形）。
検査 `★型紙2 は定数を通してしまう（だから C と対で使う）` がこれを明示している。

**★A と B と 5 は別物。** A は「一定して間違っている」（跳びでも幻でもない）、
5 は「同じ設定で 2 回」、B は「**設定を変えて**」。今日いちばん使ったのは B。

⚠ 対称性は強い型紙だが、**今日これで捕まえたバグが無い**ので候補どまり。
「思いついた型紙」を並べると中身の無い検査が増える（§1 判断3）。

### 5.2 検出器そのものの検査（`testDetectorSelfCheck`）

★**「破れなし」は、その型紙が効いている証明にならない。**
黙っているのが「健全だから」か「壊れていて何も見ていないから」か区別できない。
── これは型紙 C が言っていることの、**検出器自身への適用**。

→ 9 つ全部に、**当時の実数**（19.7dB / 8.3倍 / 1.76 / 0.486→0.000 …）を食わせて
**発火すること**と、健全なデータで**黙ること**の両方を検査している（16 件）。

### 5.3 ⚠ メッシュのシーンは吐けない

既存の検査は `AF_SceneAddInstanceBox` を並べて形を組む。**箱のシーンならそのまま
C++ に吐ける**（`Test_*` はこれ）。だが本番ステージは OBJ メッシュ（崩壊都市 8,102 三角形）で、
C++ に焼くのは現実的でない。→ **形状はデータファイルで持って検査が読み込む**形が要る。

★**箱のシーンから始めれば後回しにできる。今日のバグは全部箱のシーンで出ている。**

## 6. やらないこと（明示）

| | 理由 |
|---|---|
| イベントログからの再合成 | 入力リプレイで足りる。RNG もスティールも無い |
| ボイススタベーション / スティール / 同時発音数の検知 | **ボイス管理が無い**。作るなら先にそちら |
| sound id の多重発音検知 | sound id が無い |
| LUFS・マスキング表示 | 調整の道具の側（`TuningPanel`）の話 |
| 音源ごとの個別 PCM | 150MB。入力リプレイでソロにする |

## 7. 資料に載せるときの言い方

**「プロファイラを作りました」は弱い。**元メモ §12 が正しく書いているとおり、
録音→再生→調整のループ自体は FMOD Studio に既にある。

**強いのはここ:**

1. **検出器が自分のエンジンで実際に出たバグから来ている**
   ── 「遮蔽されているのに帯域がまっすぐなら幻」は、汎用のプロファイラには書けない。
   自分の模型の破れ方を知っている人しか書けない検出器
2. **空間エンジンとサウンドエンジンを跨いだ 1 つの記録**
   ── 既存は境界が会社をまたぐので単独で完結できない。ここは**自作の強み**
3. **見つけた破れがそのまま回帰テストになる**
   ── しかも**絶対値でなく性質で縛る**。なぜそうしたかまで説明できる

⚠ **盛らないこと。**「常時リングバッファで録画開始を押さなくていい」は事実だが、
それ単体は小さい。**判断の質**を見せるほうが効く。

### ホストから使う道（`AF_Capture*`）

★走査は**DLL の中**で回す。`AF_CaptureScan` が呼ぶのは回帰テストが呼ぶのと同じ関数。
`[ABI] 走査の結果が検査の経路と一致する` で毎回縛っている（印の数・フレーム・音源が一致）。

| | |
|---|---|
| `AF_CaptureOpen / Close / GetInfo / GetSceneName` | 開いてヘッダを照合する |
| `AF_CaptureScan` | 型紙を当てて印を返す |
| `AF_CaptureGetPcm` | マスターPCM（§3 の「波形」モード） |
| `AF_CaptureApplyFrame` | 入力を押し直す。⚠ **必ず 0 から順に** |
| `AF_CaptureEmitCase` | 印 → C++ の回帰テスト |

### 生成した検査は**ビルドに入れてある**

`AcousticEngineTest/generated_cases.inc` は `af::emit` の出力そのもの（手書きではない）。
★ここに置く意味は、生成器が「読めるコードらしきもの」ではなく
**実際にコンパイルが通って走るコード**を吐くことをビルドで担保すること。
実際、最初の版は `0` を `"0f"` と吐いていて**コンパイルが通らなかった**。

生成物には**録れた出力の数値が 1 つも入っていない**ことを検査している
（`[生成] ★吐いた検査に録れた出力の数値が 1 つも入っていない`）。
絶対値を焼くと正当なチューニングのたびに落ちて信用されなくなるため。
